# RS-10 — Messages events from a JSON body keep redacted_thinking and drop server-tool blocks (no empty text blocks)

**Spec:** docs/specs/2026-11-18-zygo-design.md §7.6 (translation: "Block types without a counterpart"), docs/specs/2026-11-25-client-model-design.md K§6.4.3 (stream obligations 2 and 3: a `redacted_thinking` block keeps its item; `server_tool_use` and `*_tool_result` blocks are dropped with `server_tool_dropped`)
**Files:** `crates/zygo-proxy/src/translate/sse.rs`, `crates/zygo-proxy/tests/translate.rs`
**Consumes:** —
**Produces:** `message_events(m: &Value) -> Vec<SseEvent>` (`crates/zygo-proxy/src/translate/sse.rs:436-463` at `ac96e1fa`) emits a `redacted_thinking` block as a `redacted_thinking` content block with its `data`, and drops `server_tool_use` / `*_tool_result` blocks with the adjustment code the streaming path uses (`server_tool_dropped`); it never emits an empty text block for them
**Acceptance:** `CARGO_INCREMENTAL=0 cargo test -p zygo-proxy --locked --test translate` → exit 0, and the tests `message_events_keeps_redacted_thinking` and `message_events_drops_server_tool_blocks` are listed and pass

## Planning notes

- Found by the RS-4 planner 2026-11-26: when an upstream answers a streaming Messages request with a JSON body, `forward.rs:550-554` turns the body into SSE with `message_events`, whose fallback arm (`sse.rs:455`) makes every block other than `thinking` and `tool_use` an empty `text` block. So `redacted_thinking` and `server_tool_use` reach the Messages client (Claude Code) as empty text blocks today.
- RS-4 does not fix it (author's call). RS-10 depends on RS-4 because both change the forward/translate seam.
- No section of either spec names the JSON answer to a streaming request by itself; the Spec line cites the block rules that the streaming path keeps.
- The Responses encoder's server-tool rule and adjustment code are at `translate/responses_client.rs:698-708`.
