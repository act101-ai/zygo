### Design of `config.sh` (one run folder, one mock, one record)

One `new_run codex-config`, one `start_mock "$RUN/rules.json"`, one `stop_mock`, one `codex_record config`: every Codex run of the part is in `isolation.txt`. Each scenario has its own prompt marker `zp-<scenario>`, its own `CODEX_HOME` `$RUN/cxh-<scenario>`, and its rules match on that marker (`"body": "zp-<scenario>"`), so scenarios never take each other's replies.

Helpers (shell functions in `config.sh`; the signatures are fixed, the bodies are the implementer's):

- `cx_home <scenario> env|auth [<extra toml file>]`: sets `CX_HOME=$RUN/cxh-<scenario>`; writes `$CX_HOME/config.toml`: `model = "gpt-mock"`, `model_provider = "mock"`, then the extra file's top-level keys (spliced before the first table), then `[model_providers.mock]` `name = "mock"`, `base_url = "$MOCK_URL/v1"`, `wire_api = "responses"`, and `env_key = "MOCK_API_KEY"` (mode `env`) or `auth = { command = "/bin/sh", args = ["-c", "echo home >>$RUN/auth-who; printf %s <DUMMY_KEY>"] }` (mode `auth`), then `[projects."<RR>"]` and `[projects."<R>"]` `trust_level = "trusted"` unless `CX_UNTRUSTED=1`, then the extra file's tables. Checks after writing: `grep -c 'base_url' config.toml` is 1.
- `cx_project <dir> <toml file>`: `mkdir -p <dir>/.codex`; copies the file to `<dir>/.codex/config.toml`.
- `cx_run <scenario> <codex exec args…>`: runs `run_codex exec --skip-git-repo-check -s workspace-write -c approval_policy="never" <args…> zp-<scenario>`; stdout and stderr to `$RUN/out/<scenario>.out` and `.err`, status to `.rc` (a failure does not stop the part); the requests the run added to `.seq` (`<record folder> <first> <last>`, from the count of `rec/[0-9]*.json` before and after; runs are sequential; the folder becomes `rec-a` for phase A runs at the restart); then removes the package copy it used (`rm -rf "${CODEX_EXE%%/p/*}"`, the `codex-pkg.XXXXXX` folder; disk: about 25 runs).
- `cx_reqs <scenario>`: the paths of the scenario's `<record folder>/<nnnn>.json`, in order (from `.seq`).
- `cx_sse <file> text <text>` | `cx_sse <file> call <name> <call_id> <arguments json>` | `cx_sse <file> custom <name> <call_id> <input text>`: writes a Responses SSE stream: `response.created`; `response.output_item.added`; for `text`, `response.output_text.delta`; `response.output_item.done` with the item (`message` with `output_text`; `function_call` {`id`, `call_id`, `name`, `arguments` (a JSON string)}; `custom_tool_call` {`id`, `call_id`, `name`, `input`}); `response.completed` with `output: [item]` and usage `{"input_tokens": 10, "output_tokens": 1, "total_tokens": 11}`. Model `{{MODEL}}`; the mock fills it. One `python3 -I` heredoc.
- `cx_tools`: from the first request of scenario `pc5-probe`, writes `$RUN/tools.env` with `SHELL_TOOL`, `SHELL_ARG` (`cmd` or `command`), `SHELL_ARRAY` (1 when that parameter's schema type is `array`), `PATCH_TOOL` and `PATCH_KIND` (`function`|`custom`), `SPAWN_TOOL` and `SPAWN_ARG`, `MCP_TOOL`. Rules: `SHELL_TOOL` = the first of `exec_command`, `shell_command`, `shell` in `body.tools[].name`; `SHELL_ARG` = `cmd` if that tool's `parameters.properties` has it, else `command`; `PATCH_TOOL` = `apply_patch` when present, its `type` gives `PATCH_KIND`; `SPAWN_TOOL` = the first name matching `spawn`; `SPAWN_ARG` = the first of `message`, `prompt`, `task`, `input` in its `parameters.properties`; `MCP_TOOL` = the first name holding `probe_tool`. A name not found is empty, and every scenario that needs it is recorded as `not-shown: no <class> tool in the request` (the stub dry run takes this path for all).
- `shell_args <command text>`: the arguments JSON for `SHELL_TOOL`: `{"<SHELL_ARG>": "<text>"}`, or `{"<SHELL_ARG>": ["/bin/sh", "-c", "<text>"]}` when `SHELL_ARRAY=1`.

Rules are appended per scenario to `$RUN/rules.json` before `start_mock` when the reply is fixed, else after the probe: the mock reads its rules at start (`mock_upstream.py:392-403`), so a scenario whose SSE depends on `cx_tools` restarts the mock. ### Implementation changes to this plan (phase A, 2026-11-25)

1. `tomllib` is not used: the `python3` first on the harness PATH is 3.9 (`/usr/bin/python3`). `cx.py` reads the `[hooks.state…]` tables of a `config.toml` by text, which also keeps them verbatim for `pc4-prewritten`.
2. `pc4-prewritten` rebuilds the source scenario's `CODEX_HOME` at the same path (`$RUN/cxh-<source>`), with the same four hook sources (same marker file, moved aside for the run): a record key or hash that names the path or the command then still matches. `trust.json` names the source as `form_from`.
3. `pc5-deny` and `pc5-deny-block` write their marker in `$R` (`zp-ran-deny`, `zp-ran-deny2`), not `$RUN`: the tool shell runs under `-s workspace-write`, so a write outside the workspace fails whether or not the hook denies it.
4. `cx_home` clears `$R/.codex` and `$RUN/other/.codex` (no project file of an earlier scenario stays); `cx_run` keeps a copy in `$RUN/proj/<scenario>/`. The step 8 URL check therefore greps `$RUN/proj` in place of `repo/.codex` and `other/.codex`. `cx_home` trusts `R`, `RR`, `$RUN/other` and its real path, each once (when `R` is `RR` a second `[projects."<R>"]` table is a TOML error); `CX_UNTRUSTED=1` writes `trust_level = "untrusted"`.
