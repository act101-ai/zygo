### How a non-WAL database reaches the hook

- No shipped zygo code makes one. The only code that creates the file is the full open (`open_bounded` has no CREATE flag, `store.rs:229-232`), and the full open has set `journal_mode = WAL` since the first commit (`git log -S journal_mode -- crates/zygo-usage/src/store.rs` → `da682dd8 zygo 0.1.0`), also at `97d8767` (`git show 97d8767:crates/zygo-usage/src/store.rs`, line 84). The journal mode WAL is kept in the file. So `old_db` (tests) is not a real upgrade path: it copies the `97d8767` schema, not its journal mode.
- Nothing guarantees WAL before the hook runs: the launcher's full open at each launch is fail-open (`crates/zygo-launch/src/launcher.rs:318`, `if let Ok(s) = Store::open(...)`), the full open fails, and leaves the mode as it was, when SQLite returns another mode (`store.rs:166-172`), and `open_bounded` checks only `user_version` (`store.rs:241-246`). A database whose mode another program set to `delete` (the file is user data under the usage directory) therefore reaches the hook.
- On a WAL database a call can still wait more than once: a `SQLITE_SCHEMA` reprepare runs the step again with `nBusy = 0` (premise), and a full open in another process adds `trims` columns one time per process (O§6.5 item 3).
- So refusing non-WAL databases in `open_bounded` would not meet O-C10 and would drop rows; the fix is a bound on the call's total wait.

### Decisions (author)

1. **Design: a second open for one call, not a deadline parameter.** `open_bounded` keeps its signature and its per-statement clock (the MCP store lives for the server's life). The hook calls a new `open_bounded_total` with the same bound, `HOOK_DB_BOUND`; no new number. The rejected option, a deadline passed into `open_bounded`, changes its signature and its MCP caller for no gain.
2. **The total clock starts at the first busy call, not at the open, and is not a sum of waits.** SQLite calls no handler when a wait ends, so a sum of waits would have to guess the end of each wait. A start fixed at the first busy call bounds every later wait inside `[start, start + bound]`, so the sum of waits is at most `bound` plus the overrun of the last sleep. The time between two waits (local work, the rest of the call) also counts: the handler gives up sooner, never later; a missed row is allowed (O§7.11). Starting at the open would count the open's own file work as waiting.
3. **One field, not a second type.** `restart: bool` in `BusyWait`; `next` sets `start = now` at `count == 0` only when `restart` is true, and otherwise only when `start` is `None` (`get_or_insert`, already there). After a give-up SQLite sets `nBusy = -1` for that wait only; the next statement's busy call gets `count == 0` and, with `restart == false`, gives up at once when the bound has passed.
4. **Tests decide no pass or fail on a clock (O§8.4).** Unit tests pass instants at fixed offsets from one origin. Real-lock tests: a lock released by another thread with a 5 s bound (success proves a wait) and a lock never released with a 50 ms bound (only the error kind is asserted). The rollback-journal database is `old_db` (usage tests) and `TRIMS_97D8767` (hook test), both in `delete` mode; `BEGIN EXCLUSIVE` there blocks readers, so the open's own read waits.
5. **Wiring proof.** The per-call property is in `BusyWait::total` (unit tests); the hook's use of it is checked by the Acceptance `grep` of the call line. A hook test with a released lock on a rollback-journal database shows the hook's read and write waits end in a row; it passes before step 4 too (bound 5 s), so it is a regression test, not fail-first.
