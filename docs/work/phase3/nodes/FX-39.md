**Decisions (author's call, FX-39).**
- D1 (R-F1, R-F2). The pin holds the workspace id of its approval: `member.launch.definition = { commit, digest, workspace }`; `check_default` sets it. The withdrawal check and the store lookup of the pinned read use that id and make no git call, so the launch folder's checkout (`.git`, a submodule, a nested repository, a git error or timeout) does not change the check. A pin with no `workspace` (written before this change, or a non-string value, read as none): the id comes from the launch folder's checkout, as before; when there is no checkout (no work tree, git error, timeout), the launch stops (fail closed) with the R§7.4 line and `which were not read (the pin has no workspace id and git found no checkout at the launch folder)`. Old pins are not rewritten (a saved pin is never replaced); `zygo up --reset` writes new ones. The pinned read still runs at the launch folder's checkout (R§10 row `up`); a member whose folder is another repository that does not have the pinned commit, and that makes the pinned read, stops with the R§7.4 line (known limit, stated in R§7.4). Rejected: (i) the id of the workspace state (`MemberCtx.ws_id`): wrong for a first pin from a nested repository's own files, and it needs the `ws`/`member` paths changed; (ii) fail closed only, with no new field: R-F2 stays (every member in a submodule stops); (iii) a repository path in the pin: more state and a path to validate, and the check does not need it. Change it if: the pinned read must work from a submodule (then the read location, not the id, changes).
- D2 (R-F1, defence in depth). R§6.2 `cwd` refuses a part equal to `.git` in any ASCII letter case (`.git`, `a/.git`, `.GIT/x`). Reason: the git dir is never a work folder, an agent started there runs next to the hooks and the config of the repository, and a case-insensitive file system maps `.GIT` to it. `.github` and `.gitignore` stay valid. `pane_cwd` does not change: it also serves user loadouts, which R-C2 does not bound, and an old pane folder in `.git` is stopped by D1. Rejected: no refusal (D1 is enough for the check, but nothing needs `.git`); a refusal of the whole value `.git` only (`sub/.git` is the same folder kind).
- D3 (R-F3). Each git call of the definition read (`SystemGit`) keeps at most 131072 bytes (128 KiB) of stdout; past that, zygo stops reading, kills the call and gets the reason `output larger than 131072 bytes`. A listing (`ls-tree`) past that, or with more than 256 entries, makes the definition **invalid**: `<dir> lists more than 256 entries` or `<dir>: the listing is larger than 131072 bytes` (`<dir>` = `.zygo` or `.zygo/profiles`). Any other call past it is **unread** (`git <call>: output larger than 131072 bytes`). Reason: invalid, as the other step 4 limits, because it is a property of the files, not a failure; both numbers are far above a valid read (32 profile files, a 64 KiB blob). Rejected: a `cat-file -s` check of the tree size before the listing (one more call, and it does not bound the read itself); a cap parameter on `GitRunner::git` (every test runner changes); unread for the listing (it would report a property of the files as a passing failure). The `.zygo.toml` read (`git_out`) does not change.

**Decisions (author's call, FX-39 review; these replace D1).**
- R1 (findings 1, 3, 6). Every definition step of a member launch runs at the checkout of the workspace's main worktree: `main_root` of the workspace record (W§7.2), the worktree that `zygo up` plans from. All worktrees of a repository share its common dir, so this is the repository `zygo up` read. The steps are the approval check, the pinned read, and the default-branch read of a member that has no pin yet.
  - The workspace id is `workspace_id(common_dir)` of that checkout (R§6.1 step 1), never a state value.
  - New field `LaunchOpts.definition_root: Option<PathBuf>`, set by the member wrapper from the workspace record.
  - A launch with a pin stops (fail closed) when `definition_root` is none or git finds no checkout there (no work tree, error, timeout). Line: the R§7.4 line with `which were not read (git found no checkout at the main worktree of the workspace)`.
  - A launch that is not a member (no `definition_root`) reads at its current folder, as before.
  - `Pin.workspace` and `Pin::approved` are removed: the pin is `{ commit, digest }` again, so there is no stale or invalid id to handle (finding 6). A pin of an older zygo is handled by the same rule. No released zygo wrote the field (FX-39 is not merged).
  - Rejected: keeping `pin.workspace` as a cross-check that must equal the computed id. It is a second user-owned value that adds a failure mode and no safety, because the computed id already comes from git.
- R2 (finding 2). After the approval check, a launch with a pin canonicalizes its pane folder (`opts.cwd`). It stops when the folder is inside the canonical common dir of the main worktree's checkout, or has more path parts equal to `.git` (ASCII case ignored) than the canonical main worktree top.
  - Line: `zygo: the folder of this member is inside a git dir (<path>); the agent was not started` (escaped), exit 1, before the session.
  - A folder that cannot be canonicalized is left to the launch.
  - `pane_cwd` stays I/O-free.
- R5 (finding 5). A `.zygo/` listing refused by a step 4 listing limit gives `Read::Invalid { workspace: true }`, so `zygo loadout list` shows `repository  workspace-files, invalid`.
