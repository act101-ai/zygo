### Decisions (author)

1. **Cap.** `shape::run` passes `VIEW_CAP_BYTES` (O§7.7 "Each stays within `VIEW_CAP_BYTES`"). The bound counts the kind view only; the O§7.8 marker that OS-28 puts before it is not counted (Open item 6).
2. **Lines.** Each line the view writes ends in `\n`. Diff sections and json text lines are verbatim slices of `text` from `text.split_inclusive('\n')` (a `\r\n` stays, O§7.3 reuse); a last line with no `\n` gets one. Log lines come from `text.lines()`; line numbers are 1-based in `text`.
3. **Diff sections.** A section starts at each line that starts with `diff --git `. When `text` has no such line, a section starts at each line that starts with `--- ` whose next line starts with `+++ ` (the two forms of `kind.rs:72`). Lines before the first section are not shown. No section → `None`.
4. **Diff list line** `<path> +<added> -<removed>`, one per section, in order. `<path>`: from the section's first `+++ ` line by `diff_path(l, "+++ ", "b/")`; when that is `/dev/null`, from its `--- ` line by `diff_path(l, "--- ", "a/")` (as `kind.rs:146-158`); a section with no `+++ ` line (binary, rename, mode change) takes the text after the last ` b/` of its `diff --git ` line. `<added>`/`<removed>`: lines after the section's first `@@` line that start with `+`/`-` (so a removed line `--- y` in a hunk counts as removed, and header lines never count).
5. **Diff fill.** View = list, then whole sections in order, then the marker `[zygo: <n> file sections not shown]` (`<n>` = sections after the last one shown, decimal; written also when 0). Section `i` is shown when list + sections `0..=i` + the marker for `n = total - i - 1` fit in `cap`; the first section that does not fit ends the walk (no later, smaller section is tried). Section 0 not fitting → `None` (O§7.7 "first unit").
6. **Json.** `json_tree(text.as_bytes())`; `Err` → `None` (a parse error, and serde_json's depth-128 limit on a 10,000-deep array). Outline lines while their bytes stay `<= cap / 2`; then text lines while the whole view stays `<= cap`; each stops at the first line that does not fit. No line written → `None`.
7. **Log.** `n` = line count. `n <= 40` → `None` (head and tail would be the whole text). Head = lines 1-20, tail = lines `n-19..=n`. Head + tail over `cap` → `None`. Between them, each line `i` in `21..=n-20` that matches `\b(ERROR|WARN|WARNING|FATAL|CRITICAL)\b|^(panic|Traceback)` (case-sensitive) is written as `<i>: <line>`, in order, while the view stays `<= cap`; the first that does not fit ends the walk. Order: head, level lines, tail. A log with no level line in the middle still gives head + tail (Open item 5).
8. **Pipeline.** Step 4 runs after the step 3 slot, only when `over(&text)`; `Some((t, s, k))` sets `text = t`, pushes `s`, sets `shaper = Some(k)`; `None` changes nothing, and `size_view` is then computed on the result as now (O§7.3 step 5).

2. **"In the view" for `must_keep`.** The log view writes a level line as `<n>: <line>`, so a `must_keep` log line is a substring of a view line, not a whole line. Recommendation: OS-29 and OS-35 check `view.contains(line)`; O§8.2/O§8.3 item 4 say "substring".
3. **Log line numbers.** The contract passes the text after steps 1-3, so `<line number>` is a line of that text; after dedup counted a run above it, it differs from the stored raw line that `result_view` reads. Recommendation: keep the contract; state "line number in the shaped text" in O§7.7, or later pass the raw line map (a contract change, not in this node).
4. **Level match.** O§7.7 says "whose level is". Recommendation: a whole word `ERROR|WARN|WARNING|FATAL|CRITICAL` anywhere in the line, case-sensitive (keeps the fixture's `<time> ERROR <name>:` form; keeping a few extra lines loses nothing).
5. **Log with no level line in the middle.** Recommendation: still give head + tail (O§7.7 gives the view without a condition); the use rule (O§7.8) drops it when it saves too little.
6. **Final view size.** The kind view is `<= VIEW_CAP_BYTES`, but the O§7.8 marker line (about 200 B) comes before it, so a kind view that fills the cap gives a final view a little over 8 KiB. The three OS-18 cases are far below (views of about 1.7, 0.8 and 4.3 KiB), so O§8.2 "view ≤ 8 KiB" holds for them. Recommendation: keep `cap = VIEW_CAP_BYTES` as O§7.7 says; if the bound must hold for the final view, change O§7.7 to pass `VIEW_CAP_BYTES` minus the marker length.
7. **Diff preamble.** Text before the first section (a `git show` or `git log -p` commit header) is not shown. Recommendation: keep; O§7.7 names only the list, sections and marker, and the marker names the stored raw text.
