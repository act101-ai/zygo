### Lock order (must never deadlock)

Locks: `op.lock` (O), `mail/sync/lock` (S), `mail/lock` (M, shared or exclusive), the state `lock` (L). Each holder, in the order it takes them:

| Holder | Order | Waits |
|---|---|---|
| `ws forget` (after this node) | O → S → M excl → L | O none (`OpHeld`), S none (zero wait), M ≤ 2 s, L ≤ `OP_WAIT` |
| sync pass (after this node) | S → M shared, one candidate or one notice at a time, released before the next git call and before S | S: child none, CLI 30 s holding nothing; M ≤ 2 s |
| `mail::send`, `mail_send`, `store::read` | M shared | ≤ 2 s |
| `forget-pane` (`admin.rs:974-1073`) | O → L (released after `update`) → M excl | M ≤ 2 s |
| `up`, `repair`, `member` undo (`up.rs:1421`, `:1629`, `repair.rs:97-101`, `cmd/member.rs:170`) | M excl after `update` returned (L released) | M ≤ 2 s |

The order is O < S < M < L for every holder: no holder of M waits for S or O, and no holder of L waits for M (`Store::update` holds L only inside its closure, `state.rs:541-553`, and no closure takes M). So no wait cycle exists; and every wait on M or S is bounded, so even a broken order would end in `Busy`, not a hang. The plan keeps this order: the forget takes M after S and after `before_remove`, and the sync takes M only inside a pass, per candidate.

### Author's calls (recorded with reasons)

1. The sync takes `mail/lock` per candidate and per notice, not for the whole import: a whole-import hold would cover git `ls-tree` and `cat` calls up to the 120 s pass deadline, and every `forget-pane`, `up` and `repair` removal would then fail its 2 s wait. Per candidate the hold is one write, one log append and one link.
2. An import candidate whose key has no record is not staged, logged or acknowledged, and writes no line: it is the S§13 limit 2 case (a folder that this workspace does not have), which writes none; the message stays on the branch and is not lost if the member comes back.
3. A staged file whose key has no record is deleted with the log unchanged, and the record check comes before the log append: M§5 deletes a member's mail with its record (forget-pane removes unread mail too), `incoming/` is never swept so a kept file would stay for ever, and the branch copy stays.
4. A lock not taken by the import stops the import for the pass (`break`), not per candidate (`continue`): 500 candidates × 2 s would pass the 120 s deadline.
5. The forget takes `mail/lock` after `before_remove` (the question and the worktree removal), not before: a lock held across a human question or a 10 s git call would make every local send and read `Busy`. The cost: a busy refusal comes after the worktree removal, which the next sync makes again (S§6.3); the state stays.
6. The forget makes a missing `mail/` (as `sync_lock` already does) so the lock exists before the rename; a `mail/` link is no mail and takes no lock (MS-21 review F3).
7. The four tests that meet a held lock (`forget_refuses_when_mail_lock_stays_held`, `import_stops_at_a_held_mail_lock`, `finish_incoming_stops_at_a_held_mail_lock`, `notice_that_cannot_take_mail_lock_is_not_sent`) run in CI, not `#[ignore = "timing: …"]`: the test holds the lock for the whole 2 s bound, so the result does not depend on time; each costs 2 s. The d4 race test uses hook points, no sleep; its only bound is `MAIL_LOCK_WAIT` against a one-file delivery.
8. No binary test is added, so no `[[marketplace]]` config is written; no test uses the network (`file://` remotes, as MS-10).
9. Not in scope, and not a widening of R1-1: a delivery that opened `mail/lock` before a forget's rename and locks it after a new workspace of the same id was written within its 2 s wait reads the new records under the old lock file. The maildir it makes then has a record (the M§5 invariant holds); only its exclusion against a removal in the new workspace is lost. It needs a `zygo up` of the same repository inside the 2 s wait. The S§8.3 step 3 inode check is the fix if a later node needs it.
