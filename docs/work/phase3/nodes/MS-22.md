### Author's calls

1. **Sends run in process; the binary runs the verbs that start no child.** `zygo mail send` and the MCP server
   start a detached `zygo mail sync --background` child (`production_spawner`, `cmd/mail.rs:420-423`;
   `zygo-mcp/src/tools/mail.rs:64-66`), which would race with the tip edits of #12 and the seams of #3, and only a
   wall-clock wait could end that race (forbidden in CI). So the CLI send is `zygo::cmd::mail::send_cli` and the
   MCP tools are `zygo_mcp::tools::mail::tools_with_sync`, each with a spawn seam that starts nothing — the same
   code as the binary minus the spawn. `zygo mail sync` (plain, `--prune`, `--take-host`, `--new-identity`,
   `--drop-host`), `zygo ws forget` and `zygo hook trim` run as the binary. Least to reverse: test-only.
2. **The binary syncs only an empty outbox.** The binary's commit-time secret pass has the 200 ms default budget
   (`DeadlinePolicy::default`, `zygo-redact/src/secret.rs:24`), which a slow CI machine can miss
   (`crates/zygo/tests/mail_remote_cli.rs:393-395`). A pass that carries outbox mail runs in process (`sync_in`,
   an hour of budget); `sync_bin` asserts an empty outbox first.
3. **Hermetic git in process.** The in-process sync starts git through `git_command`, which strips every
   `GIT_CONFIG*` variable and reads the global config of `HOME` by design (`crates/zygo-plugins/src/sync.rs:28-44`).
   The first call of `hermetic()` sets the process `HOME` and `XDG_CONFIG_HOME` to one empty folder and removes the
   git variables, as `crates/zygo-mail-sync/tests/common/mod.rs:60-88` does; every test calls it before it starts a
   process. Every git that the test starts itself is `git_cmd()` (`GIT_CONFIG_GLOBAL=/dev/null`,
   `GIT_CONFIG_NOSYSTEM=1`, `GIT_TEMPLATE_DIR=`).
4. **Two machines for #9.** B renames its host to A's host to make the collision, takes it with `--take-host`;
   A then gets a new host and `--new-identity`. #20 runs last, as no machine syncs B's dropped host again.
5. **The usage store gets a row.** No mail path writes the usage store, so a check of an absent store proves
   nothing. The test feeds `zygo hook trim` the `PostToolUse` event of a Bash `zygo mail read --name bob-q7x`
   whose output holds every marker, and asserts at least one row and no marker (O-C2 keeps the command as a name).
6. **The scanners return findings**, and one test plants a marker for each, so no scan passes by reading nothing.
7. **One test runs the walk;** both tests hold `SERIAL` (a `static Mutex<()>`), so no in-process lock meets a
   child that another test thread forks (the flock reason of `crates/zygo-mail-sync/tests/sync_pass.rs:30-34`).
