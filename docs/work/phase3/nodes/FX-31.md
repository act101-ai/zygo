# FX-31 — R§11 says a gone or withdrawn pin stops the member; the code stops only a repository-profile member

**Spec:** `docs/specs/2026-11-24-workspace-definition-design.md` R§11 (row "A pinned commit or object is gone, or its approval removed": "The member's launch stops with the R§7.4 line; the record does not change"), R§7.4 (bullets 3-6: the pinned read resolves a repository profile, for a profile name that neither the user nor the team config has; a launch in passthrough does no pinned read), R§7.2 (withdrawal: the user deletes the entry). Found in WD-20 review round 1 (H2). Evidence, read on `phase3/WD-20` after its merge of `origin/phase-3` at `3ce003ac`:
- e1 the launcher (`crates/zygo-launch/src/launcher.rs:347-378`) makes the pinned read only inside `if let Some(n) = name` and `if !cfg.config.profile.contains_key(&n)`: only a launch that asks for a profile (`--profile`, or `[user] default_profile`) that no user profile or team preset defines. `pinned_profile` (`:959-969`) gives `Pinned::Stop` for `PinnedUse::Gone`, `PinnedUse::NotApproved` and `PinnedUse::Unread`.
- e2 in passthrough (a pool member) the requested name is dropped before that check (`launcher.rs:347-353`), so no pinned read is made.
- e3 so a member with no profile, a member whose profile a user profile or team preset defines, and a pool member in passthrough all start, at a resume and at a restore by `zygo up`, when their pinned commit is gone or its approval was removed. R§7.4 bullets 3 and 6 and R§18 item 16 ("A pool member (passthrough) whose pinned commit is gone starts") describe this code; the R§11 row promises that "the member's launch stops" with no condition.

**Files:** `docs/specs/2026-11-24-workspace-definition-design.md`, `crates/zygo-launch/src/launcher.rs`, `crates/zygo/tests/workspace_definition.rs`, `docs/workspace-files.md`

**Author's call (2026-11-27): R§11 names the R§7.4 conditions; the launcher does not change.** A pin that is gone, no longer approved or unread stops only a member launch that makes the pinned read: a launch that asks for a profile name that neither the user nor the team config has, not in passthrough. Every other member launch (no profile, a user profile or team preset of the name, a pool member in passthrough) makes no pinned read and starts, also at a resume and at a restore by `zygo up`. Reason: R§7.4 lead ruling 1 says "the members and their profiles come from one approved read"; at a launch the pin is used for one thing only, the repository profile (`launcher.rs:362`, the only read of `opts.definition`; `:391` and `:468` handle `definition_out`, the pin of a default-branch read). The job is in the member record and the folder in the pane (W§7.2), not read from the pin. So a launch that applies no repository profile takes nothing from the pinned commit, and a stop of it adds no safety: it would only break the resume and the restore of members that the change of the files does not touch. Neither the code nor the spec shows a safety need for the other option (stop every pinned member). This option is also the one with the least to reverse (spec and docs text only). Text changed: the R§11 row, a new R§7.4 bullet after the passthrough bullet, R§18 item 16 (a member with no profile starts), a change-log line dated 2026-11-27, and `docs/workspace-files.md` "Members keep their files" (third paragraph).
