# OS-43 — Cap every shaped view at 8 KiB, kind view or not

**Spec:** `docs/specs/2026-11-24-output-shaping-design.md` O§8.2 (the "log: view ≤ 8 KiB" row), O§7.8 (the shaped marker)
**Files:** `crates/zygo-results/src/shape/mod.rs`, `crates/zygo-hooks/src/trim.rs`, `crates/zygo-results/tests/shape_pipeline.rs`
**Consumes:** `shape::run` (OS-15), VIEW_CAP_BYTES (existing, crates/zygo-results/src/view.rs:6), `SHAPED_MARKER_ROOM` (OS-41)
**Produces:** a shaped view that has no kind view is cut to `VIEW_CAP_BYTES - SHAPED_MARKER_ROOM` bytes, so view plus marker ≤ 8 KiB
**Acceptance:** `cargo test -p zygo-results --test shape_pipeline uncapped_` → at least one test named `uncapped_…` exists and all pass; the case: a 20,000-byte colored log at threshold 16384 gives a view plus marker of 8192 bytes or fewer

Found at OS-41 close (OS-41 review F3). Today the case gives 16,287 bytes: with no kind view, `shape::run` does not cap the shaped text (`crates/zygo-results/src/shape/mod.rs:72-83`), and the hook puts the marker before it (`crates/zygo-hooks/src/trim.rs:206`).

Measured in a scratch copy of `25e0dd24`; no tracked file changed.
- Cause. Step 4 runs only over the threshold (`crates/zygo-results/src/shape/mod.rs:72-73`), and only step 4 gets the cap `VIEW_CAP_BYTES - SHAPED_MARKER_ROOM` (`mod.rs:73`). So a text that steps 1-3 bring to 7852..=16384 bytes leaves `run` whole (`mod.rs:78-82`), and the hook writes marker + `\n` + that text (`crates/zygo-hooks/src/trim.rs:213`, `view.rs:34-43`).
- SX-4 moved the hook lines. `pending` now ends at `trim.rs:205`; `view_for` is `trim.rs:209-215`. The marker goes before the shaped text at `trim.rs:213`. `used` sizes the same final view with a 26-character id (`trim.rs:218-224`). No `trim.rs` change is needed: a cut inside `shape::run` reaches `view_for` and `used` through `Pending.shaped` (`trim.rs:201`, `:205`).
- Cut-off bytes stay stored. The hook stores `p.raw` (`trim.rs:291`), the whole O§7.2 composition built at `trim.rs:197` before `shape::run` runs (`trim.rs:201`). The cut changes only `Shaped.text`. The marker's `<n>`, `<bytes>` and `<id>` come from the stored raw text (`view.rs:34-43`), so the marker names the whole output.
- Existing helper. `str::floor_char_boundary` (std, stable; toolchain `1.98` in `rust-toolchain.toml`) is already used for the same job at `crates/zygo-proxy/src/session.rs:306`. `view::cut` (`view.rs:13-18`) caps one line at 400 chars and adds `…`; it is not a byte cap. No other byte-cap helper is in `zygo-results`.
- Cut condition. The cut applies only when `shaper.is_some() && !size_view`, which is the O§7.8 first bullet (steps 1-4 changed the text and step 5 does not run). Unchanged text (`shaper == None`) must stay whole: `kind_view_not_run_at_the_threshold` (`crates/zygo-results/tests/shape_pipeline.rs:213-218`) expects an 89,286-byte raw diff back unchanged. Step 5 already caps at `VIEW_CAP_BYTES` (`view.rs:55`). A kind view is already ≤ the cap (`kind_view.rs:101`, `:118`, `:124`, `:141`, `:150`), so the cut does not change it.
- Impact, run in the scratch copy with the change: `cargo test -p zygo-results -p zygo-hooks --no-fail-fast` fails exactly 2 tests. Both assert the uncapped behavior. `stderr_cleared_branch_counts_both_streams` (`crates/zygo-hooks/tests/shaping_hook.rs:293-306`, asserts at `:301`, `:305`) and `po2_stderr_cleared_equals_the_premise_row` (`shaping_hook.rs:325-349`, assert at `:344`; `PO2_STDERR_CLEARED = true`, `trim.rs:103`) expect `view_bytes` 13705; with the cut it is 8043. **`crates/zygo-hooks/tests/shaping_hook.rs` is not in the node's Files; this plan adds it.** The `uncapped_` tests below fail 3 of 3 without the change and pass 3 of 3 with it. ### Spec gap (for the lead; this plan does not edit the spec)

- O§7.8 first bullet says the view is "the shaped marker on the first line, then the shaped text", with no cap. O§7.3 says a step removes only "characters or lines that it recognizes". The cut of this node is in neither section. O§8.2 sets "view ≤ 8 KiB" only on the `diff, json, log` shaper rows; the measured case has shaper `clean`, whose floor is 5 %. So the 8 KiB rule for a shaped view with no kind view comes from the node contract (OS-41 review F3), not from the spec text. A decision-log row for O§7.8 is needed, of the form `| <date> | O§7.8 | author's call (lead) | a shaped view with no kind view and no step 5 had no 8 KiB cap (OS-41 F3) |`.
- The spec does not say whether the cut is on a byte or on a line end. The plan takes the byte cut that the node's Produces states ("cut to `VIEW_CAP_BYTES - SHAPED_MARKER_ROOM` bytes"), at a char boundary. A cut can thus end mid-line (for example, in `stderr_cleared_branch_counts_both_streams` the view ends with `"  "` of a `Compiling` line). The spec also gives no note in the view that says the text was cut; the marker names the stored result.
