### Decisions

1. **Routing (O§7.1, O§7.2, O§9).** Shape-on path = tool is Bash (ASCII case-insensitive), `sv.shape`, and not `parsed.file_printer`. Every other call (Read, Grep, Glob, WebFetch, `shape = false`, file printer, parse unsure) takes the shape-off path, which is today's code unchanged: early exit when `text.len() <= threshold`, the `view(&preview).len() >= text.len()` rule, stdout only, `stderr` neither read nor written (byte-equal to `97d8767`, OS-27 goldens).
2. **Command (O§7.2, O§10 row 1).** `input.tool_input["command"]` when a string → `Some(parse(cmd))`; else `None`. Row `command`: Bash → `Some(parsed.name)` or `Some("other")` when there is no string command, on both paths; other tools → `None`. A missing command still shapes (`ShapeInput.parsed = None`).
3. **Raw text (O§7.2 line 214).** `compose(stdout, stderr)`: `stdout`; if `stderr` (the `tool_response.stderr` string, else `""`) is not empty: a `\n` when `stdout` is not empty and does not end in `\n`, then `[stderr]\n`, then `stderr`. OpenCode has no `stderr` field (`hook_opencode.rs:46-48`), so raw = `output.output`.
4. **Branch (O§7.8 lines 300-301).** `opts.stderr_cleared` true: shape the raw text, count `raw.len()`, set `stderr = ""` in the output (only when `tool_response` has a `stderr` key, so the OpenCode output gains no key). False: shape `stdout`, count `stdout.len()`, leave `stderr` as it was. Both store the raw text; the marker's `<n>`, `<bytes>` are of the stored raw text.
5. **Shaping.** `ShapeInput { parsed, kind: sniff(raw.as_bytes()), threshold }`; `shape::run(src, &si)` under `catch_unwind(AssertUnwindSafe(..))`. On panic: `Shaped { text: src.to_string(), steps: vec![], shaper: over.then_some(Shaper::Size), size_view: over }` with `over = src.len() as u64 > threshold`. No stderr line for the panic (O§10 row "Shaper panics" names none). `shaper == None` → `HookOutput::None`.
6. **View (O§7.8 lines 294-297).** `size_view: true` → `view::size_view(&shaped.text, stored, &cfg)`; else `view::shaped_view(&shaped.steps, &shaped.text, stored)`. Sized first on a preview `Stored` with id `"0".repeat(26)`, `bytes = raw.len()`, `lines = raw.lines().count()` (the marker length does not depend on the id value; a ULID is 26 characters).
7. **Use rule (O§7.8 line 299).** Shape-on path only: used when `counted.saturating_sub(view.len() as u64) >= MIN_SAVING_BYTES as u64` (cast before subtracting, graph.md line 290). Else no output, no store, no row.
8. **Row (O§7.9).** `stored_bytes = counted`, `view_bytes = view.len()`, `kind = stored.kind`, `result_id = stored.id`, `shaper = shaped.shaper.as_str()`. Work-log line and `Store::put` error text as today (`trim.rs:134`, `:153-163`).
9. **Shape.** Keep `trim_in_with` under 50 code lines: a private `struct Pending { raw: String, counted: u64, shaped: Option<Shaped>, command: Option<String>, shaper: Shaper, clear_stderr: bool }`, built by `fn pending(input: &HookInput, text: String, sv: &SessionView, threshold: u64, opts: &TrimOpts) -> Option<Pending>` (both paths; `None` = no change), and `fn view_for(p: &Pending, s: &Stored, cfg: &ResultsConfig) -> String` (`shaped: None` → `view::view(s, cfg)`). The store/row/log/output tail stays one copy.

### Open question: does the 8 KiB view of O§8.2 include the marker?

Answer: **yes, the spec decides it for O§8.2**; the kind-view cap of O§7.7 is a separate, looser bound, and the spec does not say how the kind view leaves room for the marker (author's call below).

- O§8.2 line 379 measures `1 − view_bytes ÷ raw_bytes`; `view_bytes` is "as the row records them" (O§7.8 line 299), which is the final view: "The check is on the final view, marker included" (line 299). O§8.1 line 355: a case's `view` file "is the expected view", the hook output with the id masked. So "view ≤ 8 KiB" (line 387) is the final view, marker included.
- O§7.7 line 281: "Each [kind view] stays within `VIEW_CAP_BYTES`". That bounds the step's output text; the shaped marker is added after, in O§7.8 (line 294), by this node (`view.rs:30-39`).
- Code precedent: the §10.1 size view counts its own marker inside the cap (`crates/zygo-results/src/view.rs:48-51`).
- OS-29's plan (`origin/phase3/OS-29:docs/work/phase3/nodes/OS-29.md:52`, open item 6 at `:148`) passes `cap = VIEW_CAP_BYTES` and counts the kind view only. No `kind_view.rs` is on `origin/phase-3` yet (`crates/zygo-results/src/shape/` holds `clean.rs`, `command.rs`, `dedup.rs`, `mod.rs` only).
- The two bounds disagree only when a kind view is within one marker length of 8192 bytes. The shaped marker is 164 bytes plus the `<steps>` list (at most 162 bytes, all 8 names) plus the digits of `<n>` and `<bytes>` (at most 7 each below `SHAPE_MAX_BYTES`), plus the `\n`: at most 341 bytes.
- **Author's call (recorded):** O§8.2 is a bound on the final view, marker included. OS-28 builds the marker and does not cut the shaped text (no spec rule tells it how). To keep O§8.2 for every input, OS-29 should pass `cap = VIEW_CAP_BYTES - 341` (or the exact marker length); until then OS-35's floor check (O§16 item 1) catches a fixture over 8 KiB. OS-28 has no step for this.
