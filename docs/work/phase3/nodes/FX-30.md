# FX-30 — A crash-recovered delivery gets no wake and no count

**Spec:** `docs/specs/2026-11-24-mail-sync-design.md` S§8.3 step 5 ("Finish incoming", crash recovery) and step 10 ("Wake the members that got mail in step 9"), S§10.1 (the sync wakes each member that got mail), P3-4 ("Deliver and wake on the receiving machine after a fetch, with the M§7 rules"), S§19 #14 (crash seams after each step of S§8.5 "Delivery": one delivery each time). Found in FX-26 review round 2 (F-1, not caused by FX-26). Evidence, read on branch `phase3/FX-26` at `b768160e` (FX-26 re-plan 2 re-applied the deleted branch; this commit has the same `crates/` tree as the first read, and the functions below are unchanged in `sync::pass` and `import` at the branch head):
- e1 `sync::pass` (`crates/zygo-mail-sync/src/sync.rs`) calls `import::finish_incoming(sp, &c.store).map_err(|_| stop("incoming"))?` and drops the count it returns. `Report.delivered` adds only `imp.delivered.len()` from `import::run`, and the step 10 `wake(c, imp.read.as_ref(), &keys)` takes its keys only from `imp.delivered`. `import::finish_incoming` returns a count, not the keys that it delivered to.
- e2 after a crash at `after_incoming` or `after_log` (`import::run`), the staged file `<key>.<ULID>.json` is in `incoming/`. Step 5 of the next pass (`import::finish_incoming`) moves it into `mail/<key>/new/`, and nothing wakes `<key>` or counts the message.
- e3 after a crash at `after_new` or `after_ack`, the message is in `new/` and its ULID is in the imported log. The next pass's `import::run` finds the ULID in `seen` and only acknowledges it (`out.acked`, not `out.delivered`). The crashed run stopped at its seam before step 10, so no run wakes the member for that message.
- e4 the FX-26 review round 2 probe (a test in a copy of `crates/zygo/tests/mail_sync_no_content.rs`; the test that the Acceptance names, `crates/zygo-mail-sync/tests/crash_recovery_wake.rs`, takes its setup): B's member is idle with a live launcher (`StubWake { idle: true }`, which records each text that it types into the pane). A control delivery (no crash) gives `delivered = 1` and `typed = [("%3", "zygo: you have mail; read it with mail_read")]`. Then, per seam point, A sends one message and pushes, a `run_with` of B that the seam stops at that point runs, and the next `run_with` of B gives:
  - `after_incoming`: `report.delivered = 0`, in `new/`, `typed = []`;
  - `after_log`: `report.delivered = 0`, in `new/`, `typed = []`;
  - `after_new`: `report.delivered = 0`, in `new/`, `typed = []`;
  - `after_ack`: `report.delivered = 0`, in `new/`, `typed = []`.
  Each message is in `new/` once, so S§19 #14 holds, but the idle member is never woken for it and the CLI prints `0 delivered`.

**Contract:** every message that a pass or a crash recovery puts into a member's `new/` is counted in that pass's `Report.delivered`, and its member is woken under the S§10.1 rules (idle by AU26, launcher live by AU74, the M§7.3 steps and `wake_gap`; a busy member is not woken and reads at its `Stop`). This includes the `after_new` and `after_ack` cases (e3), where the message reached `new/` in a run that never woke and the next pass only acknowledges it. How a pass finds those is the planner's call within this contract, recorded as the author's call: for example, record the pending wake in the sync state before the delivery step and clear it at step 10, or wake every member with unread mail after a recovery. `import::finish_incoming` gives the keys it delivered to (or the pass reads them another way), so step 5's deliveries join the step 10 wake. A message is counted once: a pass that counts a recovered message does not count it again in a later pass. ### Author's call (coordinator's design, recorded)

1. Pending-wake record: `import::run` records `(pane key, ULID)` in `state.json` `pending_wake` before the first write of a delivery (before `make_maildir` and the staged write, so before `after_incoming`). When the record cannot be written, the line `mail sync: import <ULID>: state` is logged and the candidate waits for the next pass (not staged).
2. `finish_incoming` returns the key and ULID of each file moved into `new/`.
3. The delivered set of a pass is the union, by ULID, of step 5's result, each round's `imp.delivered`, and the entries of `pending_wake` carried from an earlier run (read at the first `state.json` load of the pass, before its first import) whose message is in `mail/<key>/new/` or `cur/` (the `deliver_staged` rule). A carried entry whose message is in neither is dropped, not counted. Each ULID counts once per pass across the rounds of the push loop. `Report.delivered` adds its size. Step 10 wakes its keys with `imp.read`, or, when the import delivered nothing, with a read under `mail/lock` shared (`Delivery::begin`, `MAIL_LOCK_WAIT`, M§5; FX-24 F2). When that read cannot begin, the line `mail sync: wake: read` is logged and no one is woken.
4. After each `import::run`, the pass takes `pending_wake` from `state.json` into its `st`, so the save at the commit does not drop the entries that the import wrote. The write that ends the pass (with `last_ok`) removes each entry that the pass considered. Limit: a crash after the wake and before that write counts and wakes the message again in the next pass (at-least-once wake, in a window of one state write). No new lock or rule.
5. A pass that stops after its deliveries keeps `pending_wake`; the next pass counts and wakes those messages.

### Author's calls made during execution

- E1 The carried `pending_wake` entries are read at the first `state.json` load of the pass (`crates/zygo-mail-sync/src/sync.rs:463-466`), not before step 5. A load before step 5 would put a `state` stop before the public check of S§8.3 step 5 (`sync.rs:440-446`), which changes the order of the existing stops. At that load no import of the pass has run, so the map holds only the entries of earlier runs.
