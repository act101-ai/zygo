### Decisions (author)

1. **The handler is a closure that owns a `BusyWait`** (rusqlite takes `FnMut + Send + 'static`, premise). `open_bounded` makes `conn` mutable and replaces `conn.busy_timeout(bound)?` with `conn.busy_handler(Some(move |count| ...))?`. No thread-local, no global.
2. **Elapsed, not requested.** At `count == 0` the handler sets `start = now`. It gives up when `now - start >= bound`; else it sleeps `min(BUSY_SLEEPS_MS[min(count, 6)], bound - (now - start))`. So no sleep is asked past the bound, and the first call at or after the bound gives up. Bound 0 gives up at the first call with no sleep. The residual overrun is the OS overrun of the last sleep, at most one sleep of at most 25 ms (O§7.11 text).
3. **Proof: two Stores on one thread.** Each `open_bounded` makes its own `BusyWait` and moves it into its own closure; rusqlite stores that closure as that connection's client data and SQLite passes it back as that connection's `pArg` (`busy.rs:73-80`). Two connections never share `start`. Test `busy_wait_clocks_are_per_store` checks the state is per value.
4. **Proof: the count restarts at 0 for each new busy statement.** SQLite sets `nBusy = 0` at each `sqlite3VdbeExec` start (`sqlite3.c:97234`), so the first busy call of each statement's run has `count == 0` and resets `start`. After a `false` return SQLite sets `nBusy = -1` and calls no more in that cycle (`:190156-190159`), so a stale `start` is never used after a give-up. Test `busy_wait_restarts_its_clock_at_count_zero`.
5. **Leftover count (accepted, safe side).** Prepare resets `nBusy` only at its end (`:149322`), so a busy call inside `sqlite3_prepare` can carry the count of the previous statement's run, and `start` is then that earlier first busy call. The elapsed time is then larger, so the handler gives up sooner, never later: O-C10 holds; the cost is a missed row, which O§7.11 already allows. A cached statement (`prepare_cached`, `insert_trim` `:312`, `insert_readback` `:327`) runs no prepare after its first use.
6. **The existing bound test changes meaning.** `open_bounded_sets_busy_timeout_to_the_bound` becomes `open_bounded_replaces_the_sqlite_busy_timeout`: `busy_timeout_ms()` is 0 for both bounds, which shows SQLite's requested-time handler is off. It fails before step 2 (100 ≠ 0).
7. **CI tests read no clock for a decision (O§8.4, O-C6).** `BusyWait::next` takes `now`; tests take one `Instant::now()` as an origin and pass fixed offsets. The real wait under a held lock is tested only at bound 0 (existing test). The on-demand O§8.5 budget 4 is OS-38's rerun, not this node's.

    /// contract; SQLite's first seven delays).
    const BUSY_SLEEPS_MS: [u64; 7] = [1, 2, 5, 10, 15, 20, 25];

    /// The bounded open's busy handler state (O§7.11, O-C10): the bound and the instant of the first busy call of the
    /// current lock cycle. SQLite's own busy timeout adds up requested sleeps, not elapsed time (OS-38).
    #[doc(hidden)]
    pub struct BusyWait {
        bound: Duration,
        start: Option<Instant>,
    }

    impl BusyWait {
        pub fn new(bound: Duration) -> BusyWait {
            BusyWait { bound, start: None }
        }

        /// The busy call `count` of a lock cycle at `now`: `Some(sleep)` retries after `sleep`, `None` gives up. SQLite
        /// passes count 0 at the first busy call of each statement run, which restarts the clock. No sleep passes the bound.
        pub fn next(&mut self, count: i32, now: Instant) -> Option<Duration> {
            if count == 0 {
                self.start = Some(now);
            }
            let start = *self.start.get_or_insert(now);
            let left = self.bound.checked_sub(now.saturating_duration_since(start)).filter(|d| !d.is_zero())?;
            let i = usize::try_from(count).unwrap_or(0).min(BUSY_SLEEPS_MS.len() - 1);
            Some(Duration::from_millis(BUSY_SLEEPS_MS[i]).min(left))
        }
    }
