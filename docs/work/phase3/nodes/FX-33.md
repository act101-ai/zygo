# FX-33 — OpenCode system text: the unread line and a foreign resume note break the prompt cache

**Spec:** — (found in the FX-9 review, F3 and F4). Two parts of the OpenCode main-role system text change between requests of one session:
- **F3 (defect).** `workspace::session_start_with_sync` (`crates/zygo-hooks/src/workspace.rs`) adds the M§7.2 unread line (`crate::mail::delivery_line`) to the OpenCode output, and the plugin's `experimental.chat.system.transform` pushes that output into `output.system` on each main-role request. The test `mail_opencode_request_text_holds_the_line_while_new_is_not_empty` (`crates/zygo-hooks/tests/workspace.rs:2094`) pins it. The choice is ML-10 D3 ("OpenCode gets the line from the per-request session text (M§7.2, AU104)") and D5 (`docs/work/phase3/nodes/ML-10.md`). Each change of the unread count changes the system text. Base spec §10.4 (`docs/specs/2026-11-18-zygo-design.md`) puts the OpenCode cache marker on the last `system` block, so a changed system text breaks the provider prompt cache from the system block on; session text design T§11 (`docs/specs/2026-11-24-session-text-design.md`) counts the OpenCode text as cached only because it "is the same on each request". M§7.2 (`docs/specs/2026-11-22-workspace-mail-design.md`) asks for the line at the prompt and at the main-loop `SessionStart`, not in a cached system block.
- **F4 (defect).** The same function adds the resume note from `inputs.and_then(note)` with no check of `ResumeNote.agent_session` against the payload `input.sessionID`. Until the plugin's `session` call (`bind_note`, D10) removes inputs bound to another agent session, a request of this OpenCode session shows a note that belongs to another one. W§9.4 and AU72/AU104 (`docs/specs/2026-11-20-workspaces-design.md`): the note inputs belong to one agent session.
**Files:** `crates/zygo-hooks/src/workspace.rs` (`session_start_with_sync`, `note`: Phase 2 code of node H1, outside this graph), `crates/zygo-hooks/tests/workspace.rs`, `crates/zygo-launch/assets/opencode-plugin.js` (only if the delivery path moves), `crates/zygo-launch/tests/opencode.rs`, `docs/specs/2026-11-22-workspace-mail-design.md` (M§7.2 text)
**Consumes:** `zygo_hooks::mail::delivery_line(n: usize) -> String` (ML-10), `zygo_hooks::session_start::fixed_item(dir: &SessionDir, agent_session: &str, build: &mut dyn FnMut() -> Option<String>) -> Option<String>` (FX-9).
**Produces:** an OpenCode main-role system text that does not change with the unread count; the unread line delivered by a path within M§7.2 that does not change the cached system blocks (the planner chooses it and states it in M§7.2); a resume note shown only to the OpenCode session that its inputs are bound to (or to any session while they are not bound)
**Acceptance:** `cargo test -p zygo-hooks --test workspace` and `cargo test -p zygo-launch --test opencode` → all pass, including tests that (1) an OpenCode main-role session's system text is byte-equal across requests while the unread count changes, (2) the unread line still reaches the agent by the chosen path, which does not change the cached system blocks, and (3) a resume note bound to another OpenCode session never shows in this session's text.

### Decisions (author)

1. **Path: the user turn, through the plugin's `chat.message` hook.** For a user message of the OpenCode main session, the plugin calls `zygo hook workspace --agent opencode --event message` with `{"sessionID": <id>, "cwd": <directory>}`; when the hook prints a line, the plugin adds it to that message as one text part with `synthetic: true`. The line is then part of the user turn, which OpenCode saves, so later requests repeat the same bytes; no `system` block and no tool definition changes. It is the OpenCode form of the M§7.2 prompt line (`UserPromptSubmit` `additionalContext`), and the first message of an OpenCode session is its main-loop start, so it also takes the place of the `SessionStart` line. The per-request system text holds no mail line.
   - Rejected: a second `system` block after the session text. §10.4 puts the marker on the last `system` block, so the changed block would hold the marker and break the cache from the system on, and 1.19.6 joins the blocks anyway.
   - Rejected: `experimental.chat.messages.transform` per request. Its input is `{}` (no session id); the line would be added to every request, not once per prompt, and a text that is not saved changes the message prefix between requests of one turn.
   - Rejected: the plugin's `prompt` call (the first `busy` status of a turn). It runs after the user message is saved, so it cannot add a part, and moving `prompt` to `chat.message` changes the AU27 turn signals (L2 D10).
2. **Main session filter in the plugin**, as the transform does for the main role (T§7.2 item 1): the `member` gate; `input.sessionID` a non-empty string and not a known child; `output.message.model.providerID === "zygo"` and `output.message.model.modelID === ZYGO_MAIN_ROLE` (non-empty); `output.parts` an array. The call is `run` directly, not the `ws` chain: it changes no state, so it does not wait for queued calls.
3. **Part id** in the plugin: `prt_` + the low 48 bits of `Date.now() * 4096 + 4095` as 12 hex digits + 14 base62 characters from `crypto.randomBytes`: the 1.19.6 form with the highest counter of its millisecond, so it sorts after the parts that OpenCode made before the hook. Fields: `id`, `sessionID`, `messageID` (`output.message.id`), `type: "text"`, `text`, `synthetic: true`.
4. **Hook event `message`** (`EVENTS` gains it, 9 values): for a main-loop payload (no `agent_id`) of a member it returns `Some(delivery_line(n))` when `unread_mail(&c) = n > 0`, else `None`. It changes nothing in `activity.json`, does not start the sync child and is not in `MARKER_LOG_EVENTS`. A mail read error is ML-10 D4: one stderr line, count 0, `None` (C6). It is agent-neutral; only the OpenCode plugin sends it.
5. **`session_start_with_sync`**: the delivery line only for Claude Code. The note for OpenCode only when the inputs have no `agent_session`, or it equals the payload `input.sessionID`; a payload with no id shows a bound note to no session. Claude Code shows and clears as today (the clear still follows `inputs.is_some()`).
6. ML-10 D3 and D5 change for OpenCode by this node; their record stays as it is (history); M§7.2 states the new path.
