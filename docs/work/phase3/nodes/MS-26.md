# MS-26 — `state::load` refuses a state.json value that `save` refuses

**Spec:** `docs/specs/2026-11-24-mail-sync-design.md` S§8.3 (the `state.json` paragraph: one rule set at read and at write), change log 2026-11-25 (S§8.3, author's call); S-C2; S§7.5 (twin check on recorded blob ids)
**Files:** `crates/zygo-mail-sync/src/state.rs`, `crates/zygo-mail-sync/tests/state.rs`
**Consumes:** `zygo_mail_sync::state::load(sp: &SyncPaths) -> std::io::Result<State>` (MS-5) at crates/zygo-mail-sync/src/state.rs:309, which today refuses a non-object with InvalidData (:315-320) and does not run check_state; `zygo_mail_sync::state::save(sp: &SyncPaths, s: &State) -> std::io::Result<()>` (MS-5) at state.rs:327, which runs check_state first (InvalidInput); `State` (MS-5), `PublicCache` (MS-5), `SyncPaths` (MS-5); the private rule set fn check_state(s: &State) -> io::Result<()> at state.rs:274 (written by MS-5, not in its Produces)
**Produces:** `zygo_mail_sync::state::load(sp: &SyncPaths) -> std::io::Result<State>` (signature unchanged; a parsed object that fails `check_state` is `Err` of kind `InvalidData`, as a non-object is; the file is left unchanged; a missing file is still `Ok(State::default())`)
**Acceptance:** `cargo test -p zygo-mail-sync --locked --test state` → all pass. A new test `load_refuses_a_value_outside_the_spec` writes, for each bad value of the existing `save_refuses_a_value_outside_the_spec` (a URL or bad name in `last_error`, a bad `public.verdict`, a bad `public.url_sha256` entry, a bad key or blob id in `pushed` and in `pending`), a `state.json` that is `good_state()` with that one value changed, and checks that `load` gives `InvalidData` and the file bytes are unchanged; then for `good_state()` that `load` gives `Ok` and `save` of the loaded value gives `Ok`. The existing tests `state_round_trip_holds_no_url`, `load_gives_default_for_a_missing_file` and `load_refuses_a_bad_file_and_leaves_it` still pass unchanged.

## Plan

**Goal:** `load` applies the `save` rule set (`check_state`) to a parsed `state.json`, so every state that loads can be saved again (S§8.3 `state.json` paragraph; change log 2026-11-25).

**Interfaces (live code, checked at 4c4f9264):**
- Consumes: `pub fn load(sp: &SyncPaths) -> std::io::Result<State>` at `crates/zygo-mail-sync/src/state.rs:309`; non-object refusal (`InvalidData`) at :315-320; `pub fn save(sp: &SyncPaths, s: &State) -> std::io::Result<()>` at :327 (runs `check_state` first, `InvalidInput`); private `fn check_state(s: &State) -> io::Result<()>` at :274; `pub struct PublicCache` at :214; `pub struct State` at :226; `pub struct SyncPaths` at :17.
- Produces: `pub fn load(sp: &SyncPaths) -> std::io::Result<State>`, signature unchanged. A parsed object that fails `check_state` is `Err` of kind `InvalidData`; the file is not changed; a missing file is still `Ok(State::default())`.

**Callers and fixtures (grep of the workspace for `load`, `state.json`, `sp.state`):**
- The only caller outside the tests is `public::check` at `crates/zygo-mail-sync/src/public.rs:153`. On `Err` it probes and saves nothing (:165-174). Before this change, a bad file loaded and the `save` at :173 failed, so nothing was written then either. The one difference: a fresh, valid cache in a file with another bad value now runs the probe and does not return the cached verdict. That is the S§8.3 rule ("never a default"). No fix is necessary.
- Fixtures that write `state.json` without `save`: `tests/state.rs:479` (`{"last_ok": 5, "later": true}`) and :487 (`{"public": {"verdict": "local"}}`). Both pass `check_state` (`local` is in `VERDICTS`, state.rs:242; an empty `url_sha256` is valid). The values at :505 and `tests/public.rs:388` are already refused before `check_state` runs. All the other fixtures in `tests/public.rs` write through `save`, so they are valid. No fixture breaks.
- Doc comments in the Files list that this change makes false: `PublicCache` at state.rs:210-211 says that a missing field "makes the cache stale". A missing `verdict` becomes `""` and `load` now refuses it. `load` at :307-308 does not name the rule set. Step 5 fixes both comments.
