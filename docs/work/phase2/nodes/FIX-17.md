# FIX-17 — W2 state store hardening: refuse a linked state folder, cap the state read at 1 MiB

**Spec:** `docs/specs/2026-11-20-workspaces-design.md` AU84, W§7.3, W§7.1 (state dir `0700`, AU2); found by W8 implementation review round 2 (R1, R6, "New FIX node (proposed)" in `nodes/W8.md`). Defect (a): `Store::op_lock`, `Store::update` and `Store::log_error` call `ensure_dir` (`crates/zygo-workspace/src/state.rs:439`), which calls `zygo_core::session_dir::SessionDir::create`; that function runs `set_permissions(0o700)` and creates files through a symbolic link at the state folder (`crates/zygo-core/src/session_dir.rs:45-49`), so any caller on a linked `<workspaces_dir>/<id>` changes the link target (W8 red line: `forget-pane --name <id>` wrote through the link). Fix (a): the store refuses a state folder that is a symbolic link, checked with `symlink_metadata` before any create, chmod, lock or write; `op_lock`, `update` and `log_error` then create nothing, change no mode and write nothing, and `op_lock` and `update` return an error that names the path (`<path>: state folder is a link`) for their callers to report; `log_error` writes nothing. The check lives in the store; `session_dir.rs` changes only if the store cannot hold it. Defect (b): `Store::read` (`state.rs:409`, `fs::read`), `list_all` and `update` read `workspace.json` without a size cap. Fix (b): every store read takes at most 1 MiB + 1 byte (`File::take`); a larger file gives `StateError::TooLarge { path }` (Round 2 F1; first `Invalid`), and `update` writes nothing over it. Spec text to apply at this node's merge, final after Round 2; it replaces the W8 Round 2 controller text for AU84 and W§7.3. ## Plan

The fix is in `crates/zygo-workspace/src/state.rs` only: one folder check that `read`, `update`, `op_lock` and `log_error` run first, one capped read of `workspace.json`, and one new `StateError` variant. The tests go in `crates/zygo-workspace/tests/state.rs`, on temporary folders only.

Builds on: (signatures in the code now)
- `Store::read(&self) -> Result<Option<Workspace>, StateError>` (`state.rs:404`), `Store::update` (`:450`), `Store::op_lock` (`:473`), `Store::log_error(&self, &str)` (`:513`), private `Store::ensure_dir` (`:439`), `pub fn list_all(&Paths) -> Vec<(String, Result<Workspace, StateError>)>` (`:605`), from W2.
- `zygo_core::session_dir::SessionDir::create` (`crates/zygo-core/src/session_dir.rs:37`), which runs `set_permissions(0o700)` on the path it is given and follows a link there.

Plan produces:
- `StateError::NotADirectory { path: PathBuf, link: bool }`: the state folder `<workspaces_dir>/<id>` is a symbolic link (`link = true`) or an entry that is not a folder (`link = false`). Display: `<path>: state folder is a link` or `<path>: state folder is not a folder`.
- `Store::read`, `update`, `op_lock` return it before they open, create, chmod, lock or write anything; `log_error` writes nothing on such a folder.
- Every store read of `workspace.json` reads at most 1 MiB + 1 byte; a file larger than 1 MiB gives `StateError::Invalid { path, reason: "state file too large" }`. `list_all` and `update` get this through `read`.

Decisions (author's call):
- D1. One new variant with a `link` flag, not two variants: callers report both the same way, through Display. The `path` is the state folder, not `workspace.json`, because the folder is what is wrong. Every other match on `StateError` in the workspace has a catch-all arm, so no caller changes; `cargo check --workspace --locked --tests` proves it.
- D2. A private `Store::check_dir(&self) -> Result<(), StateError>` runs `fs::symlink_metadata` on the state folder: a link or a non-folder gives `NotADirectory`; a missing folder is accepted, so `read` still gives `Ok(None)` and `update`, `op_lock` and `log_error` still create the folder with mode 0700; another error of `symlink_metadata` gives `StateError::Io`. `ensure_dir` calls it after the id check and before `SessionDir::create`; `read` calls it after the id check and before the file open.
- D3. `read` refuses a linked folder too, as the brief says: a read through a link would report the state of another folder. `list_all` already skips a link (`DirEntry::file_type` does not follow it); W8's `admin` checks run before the store and stay unchanged.
- D4. (Rewritten in Round 2, F6.) `session_dir.rs` does not change: the store holds the check, so the store never calls `SessionDir::create` on a link. The full limit of the check: (a) a gap remains between `check_dir` and each later open, create or mode change in the folder; a process of the same user that swaps the folder for a link in that gap is not stopped. Since Round 2 each file of the folder opens with `O_NOFOLLOW` (`lock`, `op.lock`, `errors.log`, `workspace.json`), so a link at a file is never followed and the gap is narrowed to the folder itself. (b) A symbolic link at the parent `<state dir>/workspaces`, or at any folder above it, is followed on purpose: a user may link the data folder to another disk, and that link is theirs. Only `<workspaces_dir>/<id>` and the files in it are checked. The same model as W8 `admin`.
- D5. The cap is a private `const STATE_FILE_MAX: u64 = 1024 * 1024`, the same value as `admin::STATE_MAX`; `read` uses `File::open(...).take(STATE_FILE_MAX + 1).read_to_end`, and a result longer than `STATE_FILE_MAX` is too large. A file of exactly 1 MiB reads, as `admin::too_large` (`len > STATE_MAX`) also accepts it. The cap is checked before the parse, so a large file is never parsed.
- D6. `up.rs:370` (`resolve` name claim) reads `workspace.json` of an invalid state with `fs::read`, not through the store; that read is outside this node's Files and brief, and it is reported to the controller as a finding, not changed here.
- D7. Found at the full run: W8's test `admin::a_state_file_over_1_mib_is_invalid` expected `forget big` and `forget-pane --name big` to find a 2 MiB state by its name. W8's `find` got that name from `list_all`, which read the whole file with no cap (W8 R6 names this gap). With the cap, the name in a larger file is never read, so that state is found by its id only, like any other state that cannot be read: W§12 `ws forget` matches a name among readable states (W8 D14). The test now expects `zygo: no workspace named big` for both by-name runs and gains `forget-pane --name <id>` → `<path>: state file too large`; the by-id `forget` line is unchanged. `admin.rs` is not changed: its `too_large` branch in `find` (`admin.rs:501`) stays as a guard for a file that grows after `list_all`. Files gain `crates/zygo-workspace/tests/admin.rs`.
- D8. Coordinator decision after D6: the uncapped read at `up.rs:370` is fixed here, as the same defect class. `state.rs` gains `pub(crate) fn read_state_capped(path: &Path) -> std::io::Result<Option<Vec<u8>>>`, the one cap rule: at most 1 MiB + 1 byte read, `Ok(None)` for a larger file. `Store::read` and the name claim of `preflight` both use it. In `preflight`, a state file larger than 1 MiB is not read, so it matches no name, the same as W8 `find` after D7. D6 is replaced by this. Files gain `crates/zygo-workspace/src/up.rs` and `crates/zygo-workspace/tests/up.rs`.
