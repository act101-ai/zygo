### Decisions

- D1. Reuse `cmd::start_check(rest: &[String]) -> Option<i32>` (`mod.rs:513`). It already builds the contract's `env`, `exe` and `PromptIo` for an entry point. `cmd::up` and `cmd::ws` are child modules of `cmd`, so they can call this private function. `mod.rs` does not change (it is not an M5 file).
- D2. `args` is empty (`&[]`) in both calls. `zygo up` has no agent arguments. `ws run` runs the check before it reads the state, so it does not know the saved `launch.args` yet. The contract fixes that place ("before its environment cleaning").
- D3. In `zygo up` the check runs right after the OP5 exit, before `up` reads `Paths`, the config, the folder and the binary (`cmd/up.rs:32-35`). So the check comes before any library call. It covers `--all` too, so `up --all` asks one time. On `Some(code)` (the answer `y`), `up` returns `code` and starts nothing. This is the spec's "Exit 0. Do not start the agent." (`auto-update-design.md:58`).
- D4 (controller decision, review findings 2 and 3). In `ws run` the check runs after the two id checks (`ws.rs:116-123`; an invalid id exits 1 with no request) and before `ws.rs:125`. Before the check, `ws run` reads `std::env::current_exe().and_then(std::fs::canonicalize)` (P1e). Then:
  - `Some(0)` (installed; the check already printed `updated to <new>; relaunch zygo`, `update.rs:353`): `ws run` execs that path with the same arguments (`std::env::args_os().skip(1)`) and the same, still uncleaned, process environment. It does not open a shell and does not return. The new process checks again. The check is less than 24 h old (`update.json` was written before the prompt, `update.rs:324-328`), so there is no request and no prompt. The new process then continues as a normal `ws run` and starts the member. So a loadout member record (`state = Running`, written by `up`, `up.rs:566-568`) is never left `Running` without a launcher.
  - If the exec fails, or `current_exe` failed: `ws run` prints the one line `zygo: cannot relaunch zygo ws run: <error escaped>` and continues as with `--shell` (W§8.2 step 8).
  - `Some(code)` with `code != 0` (the install failed; the check printed `zygo update: <msg>`, `update.rs:357`; the binary is unchanged): `ws run` continues as a normal `ws run`. Nothing changed, so the member starts.
- D5 (review finding 4). Decision D4 solves the resume-hint concern: on `y` the relaunched `ws run` takes the normal path. The AU61 missing-cwd hint path (`ws.rs:150-169`) is not touched and does not run in its place.
- D6. In the `ws run` tests without `y`, stdin is null. `Terminal::ask` then reads `""`, and the check continues (`update.rs:349-366`). The `zygo up` tests on the real test binary answer `n`. Each `y` test runs a copy made by the file's `setup()` (`tests/update.rs:83-90`), so the test binary is never replaced. The relaunched binary is that copy.
- D7 (controller decision, review finding 1). `Harness::env` sets `ZYGO_NO_UPDATE_CHECK=1` (the spec's env opt-out, P1d). Each M5 test that needs the check removes it with `env_remove("ZYGO_NO_UPDATE_CHECK")` and sets `ZYGO_RELEASE_BASE` and `ZYGO_TEST_ASSUME_TTY=1` itself.
- D8 (review finding 5). Every spawn or fork in `update.rs` runs under `COPY_LOCK` (the file's rule, `update.rs:10-12`). This includes `Harness::new`, `Harness::no_tmux`, `Guarded::spawn`, each `git` run, and each `PrivateServer` call. Waiting for a child does not take the lock. `setup()` takes the lock itself, so it is never called inside `locked`.
