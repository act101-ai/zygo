### Decisions

- D1. A member is the AU58 marker: `ctx.view.workspace.is_some()`. The launcher, not the adapter, handles `--settings` (D3), so the adapter has one rule. `LaunchCtx` gets no new field.
- D2. Member hook commands are `<zygo> hook workspace --event <e>`, the form of the existing `work --event begin` entries and of H1's `workspace_hook_cli`. Entries: `PreToolUse` matcher `Agent` → `pre-tool`; `Stop` → `stop`; `StopFailure` → `stop`; `SubagentStart` → `subagent-start`; `SubagentStop` → `subagent-stop`, next to the work entry when work units are on. Claude Code runs all matching hooks of an event in parallel (https://code.claude.com/docs/en/hooks), so the order of entries is not significant; the tests check membership, not position. `SessionStart` and `UserPromptSubmit` keep their one existing entry (W§9.1: "existing").
- D3. `--settings` (review minor 2): when `LaunchOpts.member` is set and the Claude Code arguments hold `--settings` before any `--`, `Launcher::run` uses `None` as the member before it builds the view. So the view has no marker, the child gets no `ZYGO_WORKSPACE` and no `ZYGO_PANE` (the AU58 filter removes inherited ones), and the adapter writes no member hook. The adapter's `build` prints `SETTINGS_WARN` as today; the launcher prints `MEMBER_SETTINGS_WARN` (the AU59 text) right after the spec lines (`launcher.rs:571-573`), so the order is `SETTINGS_WARN`, then AU59. The callers (M2 per AU102, M3 per W§8.4) already pass `None` for `--settings`; this is the second guard.
- D4. One flag source (review B1). `zygo-launch` depends on `zygo-workspace`: no cycle, because `zygo-workspace` depends on `zygo-core`, `zygo-config`, `zygo-work` and `zygo-proxy` only (`crates/zygo-workspace/Cargo.toml`), and none of those depends on `zygo-launch` (AU103, W§20 #15 (e)). W4's table gains a class `Session` for the session flags (removed as `Remove` is; `filter` and `removable` do not change). New functions in `args.rs`: `has_session_arg` (W4's walk, which handles short clusters, flag values and `--`, `args.rs:222-271`, reports a `Session` flag), `session_flags` (every name of the `Session` flags of the agent's table), `flags` (the long name of every table flag the walk meets before `--`, in order). The adapters call them; no second list exists, so no parity test is needed. `--teleport` is in the Claude Code list (`args.rs:52`).
- D5. `--` rule (review minor 1): every check of a flag in the launch arguments goes through W4's walk, which stops at `--`: `has_session_arg`, the `--settings` check of `build` (`SETTINGS_WARN` and its log line), and the launcher's member clear. `claude_code::has_user_settings(args)` = `flags(Agent::ClaudeCode, args).contains(&"--settings")`, used in both Claude Code places. `--bare` keeps the existing `has_flag`.
- D6. `preassign_args(id)`: Claude Code `["--session-id", id]`; OpenCode keeps the default `[]` (W§8.3). `resume_args(id)`: Claude Code `["--resume", id]`; OpenCode `["-s", id]` (AU3). M2 makes the UUID.
- D7. Plugin gate: the workspace calls run only when `process.env.ZYGO_WORKSPACE` is a non-empty string. It is a cheap gate in the agent process; H1 still decides from the view marker only (AU58). The launcher sets the name only for members (`launcher.rs:589-592`) and removes it for every other launch (`env.rs:35`). Known limits: `opencode run --attach <url>` runs the plugin in a server process without the member environment, so no member events; `--pure` (`fixtures/opencode/help.txt:38`) loads no plugin, so no member events.
- D8. Plugin main session (review minor 4, 5): the main session is the latest session with no `parentID` that the plugin sees become active: a `session.created` event whose `info` has no `parentID`, or, before any such event (a resume), the first event that carries a session id. The evidence shows no session-switch event (`fixtures/opencode/workspace/plugin-event-types.txt` lists none). A `session.*` event whose `info.parentID` is set adds its id to the child set; a child id is never the main session. `parentID` is an optional field of the session info of OpenCode 1.19.6 (`~/.opencode/bin/opencode`, read as text: `parentID:G($n)` in the session schema). When the main session changes, the plugin sends `session` again with the new id (H1 then writes `agent_session`) and sets `idleNow = true`. The session id of an event is read as P2's probe read it (`scripts/premises/live-workspace.sh:574-578`).
- D9. Plugin `stop`: an event of the main session that is `session.idle`, or `session.status` with status `idle`, sends `stop` and sets `idleNow = true`. PW4 4.3 saw both after a turn (`fixtures/opencode/workspace/pw4.txt`); H1's `stop` only sets `busy = false`, so two calls per turn end are harmless.
- D10. Plugin `prompt` (turn start; author's call 2026-11-22): the first `session.status` event of the main session with status `busy` while `idleNow` is `true` sends `prompt` and sets `idleNow = false`. `idleNow` starts `true`. A `retry` status and events of other sessions change nothing. Evidence and choice:
  - `chat.message` is not chosen: P2's probe registered it (`live-workspace.sh:587`), but no fixture records that it fired (`pw4.txt` names only `event` and `tool.execute.before`; the probe's `events.jsonl` was not kept). The author's rule then picks the fallback.
  - `session.status` reaches plugins: `plugin-event-types.txt`; PW4 4.3 saw it with status `idle` (the `IDLE` selector, `live-workspace.sh:556`, reads `properties.status.type`, `:579-582`).
  - The `busy` value is not in a fixture. OpenCode 1.19.6 (binary read as text, not run) defines `session.status` as `{sessionID, status}` with status types `idle`, `retry`, `busy` (`identifier:"SessionStatus"`), and sets `{type:"busy"}` at each step of its prompt loop (`Prompt.run`) and in the runner's `onBusy`. One turn gives many `busy` statuses, so only the first after an idle sends `prompt`. E2 re-checks it live (controller section).
- D11. Synchronous decisions (review B2): the `event` handler reads the event, updates `main`, the child set and `idleNow`, and queues the calls, all before any `await`; it returns without waiting for the calls (review minor 7). All workspace calls of one plugin instance run one after another on one promise chain, so they reach zygo in decision order (`session` before `prompt` before `stop`), even when OpenCode runs handlers at once. `run` never rejects, so the chain cannot break. `run` gains a third parameter `extra = []`: `["hook", name, "--agent", "opencode", ...extra]`; the existing calls do not pass it.
- D12. Plugin `pre-tool`: in `tool.execute.before`, for a member and `input.tool === "task"`, the plugin queues `pre-tool` on the chain and waits for it, then a deny throws its reason and `guard` does not run; else the existing `guard` code runs. Worst-case wait: each call has the 10 s timeout of `run` (`opencode-plugin.js:15-18`), so the dispatch waits at most 10 s for each call queued ahead plus 10 s for its own (round 2: no fixed count of queued calls is claimed). The usual wait is the run time of short `zygo` processes.
- D13. `session` clears `busy` (review minor 6): H1's `session` event sets `busy = false` (H1 contract text in the controller section), so an OpenCode restart after a crash in the middle of a turn clears a stale `busy`. Known limit: `opencode run` can exit before its queued `stop` runs; the next `session` clears it.
- D14. Conformance (review minor 11): a second table `| Agent | WA-1 | WA-2 |` under a new section `## Workspace capabilities`, same cell form. Claude Code WA-1 partial (PW16 16.2 failed: a resume with another `CLAUDE_CONFIG_DIR` finds no conversation; AU61 reuses the saved one); WA-2 partial (PW7 7.2, 7.5). OpenCode WA-1 partial (TUI resume with `-s` not verified live; E2 re-checks); WA-2 partial (no subagent events; the busy value of the turn start not in a fixture).
- D15. `scripts/check-conformance.sh` checks each table by its header row: the data rows are the table rows right after the header, so the A-1..A-21 check no longer counts the WA rows. One function checks both tables.
