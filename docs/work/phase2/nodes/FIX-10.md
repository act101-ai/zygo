# FIX-10 — Record the upstream error type and message of a non-2xx passthrough answer (FIX-8 follow-up)

**Spec:** `docs/specs/2026-11-18-zygo-design.md` §14 (usage store, metadata only: the `requests` columns, "Never: bodies, prompts, tool inputs …"), §12.4 (passthrough), §7.3 (a 5xx or 429 is kept as the last answer and relayed); found by FIX-8 (`docs/work/phase2/nodes/FIX-8.md` "Root cause", verdict `not determined`: in 24 of 24 passthrough sessions the first `auxiliary` request is answered 429, and no record holds the upstream error text, because the usage row stores the status only, `crates/zygo-usage/src/schema.rs`). Code: a 5xx or 429 is kept as `last` (`crates/zygo-proxy/src/forward.rs:446`) and relayed to the client (`:465-469`); the response tee copies a non-streamed body up to 4 MiB for parsing (§14). Change: for a passthrough request whose upstream answer is not 2xx, zygo parses the relayed body as the Anthropic error form `{"type":"error","error":{"type":…,"message":…}}` and writes one row to a new usage table `upstream_errors` (`ts`, `session`, `request_class`, `model`, `status`, `error_type`, `error_message`), created with `CREATE TABLE IF NOT EXISTS` so an existing `usage.db` needs no migration and `RequestRow` and its literals do not change. `error_message` keeps at most 300 characters, with control characters replaced by a space; no request byte, header or credential is written. A body that does not parse writes the row with `error_type` and `error_message` empty. The relayed answer to the client does not change (status, headers, body). Retention as `requests` (`[usage] retain_days`). The node adds a dated note to §14 of the base spec for the new table and one base-spec change-log line: "§14: table `upstream_errors` records the upstream error type and message of a non-2xx passthrough answer; LIV-1 D8, FIX-8, FIX-10."
**Files:** `crates/zygo-usage/src/schema.rs`, `crates/zygo-usage/src/store.rs`, `crates/zygo-usage/tests/store.rs`, `crates/zygo-proxy/src/forward.rs`, `crates/zygo-proxy/tests/passthrough.rs`, `docs/specs/2026-11-18-zygo-design.md`
**Consumes:** —
**Produces:** `schema::UpstreamErrorRow { ts: i64, session: String, request_class: Option<String>, model: String, status: u16, error_type: String, error_message: String }`, `store::Store::insert_upstream_error(&self, row: &UpstreamErrorRow) -> anyhow::Result<()>`, `store::Store::upstream_errors(&self, session: &str) -> anyhow::Result<Vec<UpstreamErrorRow>>`
**Acceptance:** `cargo test -p zygo-proxy --locked --test passthrough && cargo test -p zygo-usage --locked --test store && cargo test --workspace --locked --no-run` → 0 failed, including, with the mock upstream of `passthrough.rs` (`Upstream::answer`): an `auxiliary` request answered 429 with `{"type":"error","error":{"type":"rate_limit_error","message":"limit"}}` gives one `upstream_errors` row with status 429, class `auxiliary`, `rate_limit_error` and `limit`, and the client still gets the same status, `retry-after` and body; a 200 answer gives no row; a 500 with a body that is not JSON gives one row with empty type and message; a message of 1000 characters with a newline is stored as 300 characters with no control character; a request whose body holds a tracer word writes no row field that holds it; and `store.rs` creates the table on an existing database that has only the old tables
