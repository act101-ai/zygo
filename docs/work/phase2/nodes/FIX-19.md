# FIX-19 — OpenCode plugin sends tool start and end to the member hooks

**Spec:** `docs/specs/2026-11-20-workspaces-design.md` W§9.1 (`tools_running`), AU26 (W10 round 3, running tool), AU27; found by W10 implementation review rounds 2-3 (C24, C33 in `nodes/W10.md`). The plugin (`crates/zygo-launch/assets/opencode-plugin.js`) uses the hook names that it already uses and that the pinned OpenCode loads: `tool.execute.before` and `tool.execute.after` (plugin lines 91-105; `fixtures/opencode/binary-names.txt`, `load-result.json`). For a member, and only when `input.sessionID` is the main session of the plugin's `step` logic (never a `task` child session): `tool.execute.before` queues `ws("pre-tool", { sessionID, tool_name })` for every tool, with `tool_name` `"Agent"` for `task` (the existing deny call, now for every tool) and the tool's own name for the others, and keeps the deny of the `Agent` answer; `tool.execute.after` queues `ws("tool-end", { sessionID })` first, before `trim` and `work`. The plugin's `prompt` call (a main-session `busy` status after idle) resets the count to 0 in H1, as `UserPromptSubmit` does for Claude Code; the plugin sends nothing more for it. An Esc in OpenCode that ends a tool without `tool.execute.after` leaves the count up until the next `prompt`, `stop` or `session` call. Both go through the one `ws` chain, so they keep their order with `prompt` and `stop`. A `pre-tool` that denies adds nothing (H1), and a tool that the `guard` call then denies has no `tool.execute.after`: the count stays up until the turn's `stop`, the safe side.

**Acceptance:** `cargo test -p zygo-launch --test opencode` → pass, including: a main-session tool call sends `pre-tool` then `tool-end` in that order; a `task` child session's tool sends neither; a launch that is not a member sends neither; the `Agent` deny still throws; a `prompt` after a `pre-tool` with no `tool-end` is sent in that order (the H1 reset).
