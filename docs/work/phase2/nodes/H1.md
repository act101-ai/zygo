### Decisions

Each decision is the author's call (2026-11-22) inside the operator's requests, or a controller decision of review round 1 where it says so. Where the spec allows two readings, the decision keeps the user's work running: busy over idle, a lost change over a broken agent (C6), no time limit, cap or clean-up that ends or deletes anything.

- D1. Membership (AU58). `run` reads only `ZYGO_SESSION_DIR` through `env`; none or empty gives `Ok(None)`. The workspace id and the pane key come only from `view.workspace.member` of that folder. `ZYGO_WORKSPACE` and `ZYGO_PANE` are never read. A view with no `workspace` is not a member: `Ok(None)`, nothing written, no folder made.
- D2. Session folder and view (FIX-17 classes; controller decision 2). `check_folder`: the `ZYGO_SESSION_DIR` path must be absolute, and its last part, seen with `symlink_metadata`, must be a folder that is not a link; else `Err` with `ZYGO_SESSION_DIR is not an absolute path: <esc(path)>`, `<path>: session folder is a link` or `<path>: session folder is not a folder`. A link above the last part is followed, as FIX-17 does for the state folder. `read_view`: no `view.json` gives `Ok(None)`; else `view.json` is opened read-only with `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC` on unix and the opened handle must be a regular file; the whole file is read (no cap) and parsed. Errors: `<view path>: is a link; not read`, `<view path>: is not a regular file; not read`, `<view path>: <io error>`, `<view path>: <serde error>`. On other systems the open has no flag and the handle check stays. Who uses them: the `workspace` hook (`run`), which is registered only for members (Claude Code, `ClaudeCode::hooks`) or called only when `ZYGO_WORKSPACE` is set (OpenCode plugin `:42`): `check_folder` `Err` is returned (so `guarded` writes one stderr line, exit 0, nothing opened inside a refused folder), a `read_view` `Err` writes one session-log line with its text and changes nothing. `prompt` (D9) uses both silently. `session-start` (D15) keeps today's `SessionView::load` and uses neither for its read.
- D3. Marker values (AU84; controller decision 10). A `ws_id` that fails `valid_ws_id` builds no path, so no `errors.log` is reachable (it lives in `<workspaces_dir>/<ws_id>/`): one session-log line `invalid workspace id "<esc(ws_id)>" in the session view`, nothing changed (C11). A pane key that fails `valid_pane_key`: one `errors.log` line `invalid pane key "<esc(pane)>" in the session view` in that workspace's state folder, nothing changed. Neither denies a call or blocks a prompt.
- D4. Main loop. An input is the main loop when its JSON object has no `agent_id` key (W§9.1, "the test of §8.3"; `HookInput::has_agent_id` uses the same test). OpenCode payloads carry no `agent_id`: the plugin sends only main-session events (AU27; FIX-19 filters the tool events by the main session), so each one is the main loop.
- D5. Effects, main loop only unless named (W§9.1 table, AU27, AU43, FIX-20 D4):

  | Event | `busy` | `tools_running` | `running` | Other |
  |---|---|---|---|---|
  | `pre-tool`, not denied | — | `saturating_add(1)` | — | D8 first, for `tool_name == "Agent"` only |
  | `tool-end` | — | `saturating_sub(1)` | — | — |
  | `prompt` (OpenCode), `user_prompt` (Claude Code, D9) | `true` | 0 | — | — |
  | `stop` (`Stop`, `StopFailure`, OpenCode idle) | `false` | 0 | — | — |
  | `session-end` | — | 0 | — | `busy` stays: W§9.1 names no `busy` change |
  | `session` (OpenCode) | `false` | 0 | — | D10 record write, D12 snapshot, D14 note clear on an id change |
  | `subagent-start` (any loop) | — | — | `subagent_start(agent_id, agent_type)` | needs a string `agent_id`; a missing or non-string `agent_type` is `""` |
  | `subagent-stop` (any loop) | — | — | `subagent_stop(agent_id)` | needs a string `agent_id` |

  An input with an `agent_id` key changes neither `busy` nor `tools_running`. Every `activity.json` change is one `activity::update(dir, activity::LOCK_BOUND, ..)`. Only `pre-tool` can print (the deny JSON); every other event returns `Ok(None)`.
- D6. `activity.json` guard. Before each `activity::update`, `symlink_metadata(dir.activity_json())`: missing or a regular file goes on; a link gives the session-log line `<activity.json path>: is a link; not changed`, any other entry `<activity.json path>: is not a regular file; not changed`, and no update. This closes the link and FIFO cases in the hook; FIX-22 (C9) fixes the reader and then removes this guard.
- D7. Logs. Activity failures (D6, and each `Err` of `activity::update`, the AU56 bound among them) write one line to the session log: `workspace hook <event>: <error text>`. Failures of the state folder's own files and of the member record write one line to `errors.log` through `Store::log_error` with the same form (`StateError::Busy`, the `workspace.json` bound of W§7.3, gives `workspace hook <event>: workspace state is locked`). A state folder that `Store::read` refuses as `NotADirectory` gets its line in the session log, since `errors.log` lives in that folder. Every session-log line goes through `SessionDir::append_log` (D21). `<event>` is the CLI event name, `prompt` for `UserPromptSubmit`, `session-start` for `SessionStart`. The hook returns `Ok(None)` after it logged, so `guarded` adds no stderr line and the exit is 0 (AU56).
- D8. Dispatch deny (W§9.2, AU83, W§18 #44). Only `pre-tool` with `tool_name` exactly `"Agent"` reads the phase, with `Store::phase_unlocked` (no lock). `Draining`: `drain_block_dispatch` from `zygo_config::load(&LoadContext { paths: paths.clone(), repo: None, team: None })` (the table is user config only, W-C5); a load error counts as `true`, the OP6 default; only when it is `true` does the hook call `Store::op_lock_free`; held gives the deny with `DRAINING`. `Stopping`: `op_lock_free`; held gives the deny with `STOPPING`. Any other phase, a missing or unreadable state, or a free `op.lock` gives no deny, and in any other phase `op.lock` is not opened. The deny is `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"deny","permissionDecisionReason":<reason>}}` as one JSON text; it applies with or without `agent_id` (W§9.2 names no loop); a denied call changes no count. No other tool reads `workspace.json` or touches `op.lock`.
- D9. Claude Code prompt (controller decision 2). `prompt::run_member` first tests the prompt with the regex of `run_with` (the `prompt` string, trailing whitespace trimmed). A match runs `run_with` and nothing else: a `/zygo:` line sets no `busy` (W§9.1). Else, with a session folder, `workspace::user_prompt`. `user_prompt` cannot know membership before it reads the view, so everything before a member view is known is silent: a `check_folder` `Err`, a `read_view` `Err`, no `view.json` or a view with no marker gives `Ok(None)` with no log line, no stderr line and no write; a launch that is not a member so prints and writes exactly what it does today (nothing). For a member view: D3 checks (with their log lines); a phase `Stopping` while `op.lock` is held prints `{"decision":"block","reason":"zygo: workspace is stopping"}` (AU86, AU83) and changes nothing; else the main loop gets `busy = true`, `tools_running = 0`. `Draining` blocks no prompt. The OpenCode `prompt` call is never blocked (AU86).
- D10. Member record at a start (AU92 as amended by FIX-20, AU60, AU104; controller decisions 6, 7). Inputs: the payload id (`session_id` for Claude Code `session-start`, `sessionID` for the OpenCode `session` call): a non-empty string is the id; a missing key, a non-string value or `""` is no id (no line is logged for it). The hook first reads the state with `Store::read`: `Ok(None)` writes nothing, logs nothing and makes no folder; an `Err` logs (D7) and writes nothing. Then one `Store::update(snapshot::HOOK_WAIT, ..)`, which keeps `before = m.agent_session.clone()`: no record for the pane: `Err` `no member record for pane <key>; not changed` (logged). First start: `pending` is `Some` and `pending.zygo_session == view.session`; then `zygo_session = Some(pending.zygo_session)`, `agent_session = id.or(pending.agent_session).or(before)`, `state = Running`, `pending = None`, and the AU60 clear: `closed_units` and `interrupted` empty, `clean_stop = false`, `note_pending = false`. Not first and `zygo_session != Some(view.session)`: the record belongs to another start: `Err` `member record of pane <key> belongs to another session; not changed` (logged). Not first, same session: an id that differs from `agent_session` is written. So no event replaces a stored id with none. A record equal to the one read is not written: the closure returns the private error `Unchanged`, which the hook takes as "no write", with no log and no pending check. The id changed when the written `agent_session` differs from `before`. A later `SessionStart` (after `/clear` or a compaction) is not first, so it clears nothing that `down` wrote meanwhile. Known limit: when the first start loses its 1 s bound, `pending` stays, the member wrapper commits it at exit (W§8.2 step 7), and the AU60 clear of that start does not happen (C4).
- D11. Agent session id and resume (controller decision 7). Any non-empty string is recorded as it is; there is no length or character rule. The resume path keeps such an id one argument: `ws run` (M2) passes `LaunchOpts.agent_session = Resume(id)`, the launcher inserts `AgentAdapter::resume_args(id)` (`launcher.rs:215`), Claude Code gives `--resume=<id>` and OpenCode now gives `--session=<id>` (step 3; evidence in review round 1 item 7). An id that the agent does not know fails the resume, which W§8.2 step 7 and AU12 already handle. Every place that prints an id escapes it (`esc`, as `up.rs:709` does).
- D12. Snapshot after a write (W§7.3, W§7.4). Only a write of `workspace.json` by this hook is followed by the pending check; an `activity.json` write is not (W§7.3: the writers of `workspace.json` check). After the write: `want = Some(false)` when the id changed (D10), else `None`; `taken = snapshot::take_pending(paths, ws_id)`; no child when both are `None`; else one child with `--force` when `taken == Some(true)`.
- D13. Detached child (controller decision 11). `Command::new(zygo)` with the arguments `ws`, `snapshot`, `--ws-id`, `<ws_id>`, and `--force` when set; stdin, stdout and stderr `Stdio::null()`; on unix `current_dir("/")` (the child holds no worktree) and a `pre_exec` that calls `libc::setsid()` and fails the spawn when it returns -1; the environment is inherited. The hook does not wait for the child, which `init` reaps when the hook exits (`#[allow(clippy::zombie_processes)]` on the function, with that reason). A spawn `Err(e)`: `snapshot::queue_pending(paths, ws_id, force)`, then one `errors.log` line, `cannot start the snapshot: <e>; snapshot.pending set again`, or `cannot start the snapshot: <e>; snapshot.pending not set: <q:#>` when the queue fails. A child that starts but fails queues the flag itself: `snapshot_child(paths, ws_id, force, body)` runs `body` under `catch_unwind(AssertUnwindSafe(..))`; `Ok(())` gives `Ok(())`; an `Err(e)` or a panic calls `snapshot::queue_pending(paths, ws_id, force)` and gives `Err` with the text `<e:#>` (a panic: `the snapshot panicked: <message>`), followed by `; snapshot.pending not set: <q:#>` when the queue fails. M1's `zygo ws snapshot` runs its whole body (multiplexer build, `snapshot::run`) as `body` with its own `--force` (C10). Known limit: a child killed by a signal queues nothing; the next trigger snapshots. On other systems the child has no `setsid` and no cwd change; it never runs there (OP5).
- D14. Resume note (W§9.4, AU60, AU72; controller decisions 1, 9). The inputs are `view.workspace.resume_note`. `note(n)`: `clean_stop == false` gives only `zygo did not stop this session cleanly; the list of closed units was not saved.` (the lists were not saved, AU42); else the interrupted line `zygo stopped this session while subagents <items> were running; their results were lost; dispatch them again if still needed.` when `interrupted` is not empty, with `<items>` = each `<esc(type)> <esc(id)>` (an empty type prints `<esc(id)>` alone) joined by `, ` in the stored order, then the units line `Units <esc(u)>, <esc(u)> were closed when zygo stopped this session; call work_begin to open them again if work continues.` when `closed_units` is not empty; lines joined by `\n`; `None` when `clean_stop` is true and both lists are empty. The output text is the session text, an empty line, then the note (the note alone when the session text is empty). Claude Code (AU60 order): (1) the hook writes the whole hook output (`HookOutput::Json` of `run_in`'s form, as `to_stdout` renders it) to `out` and flushes; a write error returns `Err` with nothing written to any file, so `pending` stays and the next `SessionStart` is still the first one; (2) the record write of D10; (3) the view is saved again with `resume_note = None` whenever it held inputs (also in the no-note case and when the record write failed; a save failure gives one session-log line); (4) `run_member` returns `HookOutput::None`, so the cmd layer prints nothing more. The note is printed once; a failed view save can print it again at the next `SessionStart`, never lose it. OpenCode: the plugin's `experimental.chat.system.transform` calls `session-start` on every model request, so `session-start` adds the note to every output and writes nothing; the plugin's `session` call removes the inputs from the view (`read_view`, `resume_note = None`, `save`; a failure gives one session-log line) when its record write changed the id (D10). A resumed OpenCode session reports the stored id, so the note stays for the whole resumed agent session; a new main session clears it. With no state or a lost bound nothing changes and the note stays, the safe side.
- D15. Agents and launches that are not members (controller decision 2). `session_start::run_member`: a `SessionStart` with an `agent_id` key gives `HookOutput::None` and changes nothing (as `run_in`). Then `SessionView::load(dir)?`, today's read with today's error. A view with no marker: the output of `run_in`, through the same private functions, and no other effect: no new refusal, no log line, no stderr line, any size. A member view: `check_folder(dir)` and `symlink_metadata(view_json)` (a regular file, not a link) run first; a refused folder skips the member part with no line (nothing is written into a refused folder), and a `view.json` that is a link or not a regular file skips it with the session-log line `workspace hook session-start: <view path>: is a link; the member record and the resume note are not changed` (or `is not a regular file; ...`); the output is then `run_in`'s. Else D3, then `workspace::session_start`: Claude Code main loop: D14 Claude Code order with D10 on the payload's `session_id`; OpenCode: D14 OpenCode (the note only; the plugin's `session` call owns the record, AU104).
- D16. State ownership. H1 writes in `workspace.json` only these fields of the member record of its own pane: `pending`, `zygo_session`, `agent_session`, `state`, `closed_units`, `interrupted`, `clean_stop`, `note_pending`; never `phase`, `windows[]`, `panes[]` or another member (W§7.3: the snapshot owns the layout, `up` and `down` own the phase). In `activity.json`: `busy`, `tools_running`, and `running` through the two W9 methods. In `view.json`: only `workspace.resume_note`, set to `None`. It makes no state folder for a workspace with no state (D10 reads first), with one exception: the `errors.log` line of D3 for an invalid pane key, which `Store::log_error` writes into the folder of a valid id (AU84). `snapshot_child` writes only `snapshot.pending`.
- D17. Failure part way. The parts of one event are independent: in `session`, the activity change, the record write and the note clear each run, and the failure of one does not skip the next (the note clear needs a written id change); in Claude Code `session-start`, the note is printed before any write, and a failed record write does not stop the view save. Each file write is one rename, so no failure leaves a half-written file.
- D18. CLI (controller decision 12). `TABLE` gets `Hook { name: "workspace", run: workspace_hook, reads_stdin: true }` after `guard`. `workspace_hook`: no `--event` gives `Err` `workspace: --event is required`; else `workspace::run(event, &serde_json::to_vec(&input.raw)?, &Paths::from_env(), &|k| std::env::var_os(k), &std::env::current_exe().unwrap_or_default())`, `Some(text)` as `HookOutput::Text(text)`, `None` as `HookOutput::None`. `run` checks in this order: (1) an event outside `EVENTS` gives `Err` `workspace: unknown event "<esc(event)>"`; (2) then it reads `ZYGO_SESSION_DIR` through `env`: none or empty gives `Ok(None)`; (3) input that is not JSON gives the serde error, and a JSON value that is not an object gives `hook input is not a JSON object`; (4) `check_folder`, `read_view` and D3. An empty `current_exe` makes the spawn fail, which D13 handles.
- D19. No time limit. H1 adds no timer, expiry, cap or clean-up. Its only waits are the 1 s lock bounds of AU56 and W§7.3; a bound that passes loses this hook's own change and ends nothing. A lost `tool-end`, an Esc during a tool, or a `pre-tool` that another hook then denies keeps `tools_running` above 0 until the next `prompt`, `stop`, `session-end` or OpenCode `session`: the member stays busy, the safe side.
- D20. Tests. `crates/zygo-hooks/tests/workspace.rs` is `#![cfg(unix)]` (the stub program is a shell script; workspaces need tmux, OP5). Every test takes `SERIAL` (scripts are written while other tests fork, ETXTBSY). No test asserts a wall-time bound. Each wait waits for an event (a file appears, a thread answers) with a 5 s bound that no correct run reaches. Locks are held through the producers' own functions (`activity::update`, `Store::update`, `Store::op_lock`), never by sleeps. The FIFO cases run the hook in a thread and wait for its answer for at most 5 s, so a hook that waits fails the test instead of hanging it. The SIGKILL case uses a helper process, as the contract says. The open count of `op.lock` uses inotify (`cfg(target_os = "linux")`).
- D21. One session-log writer (controller decision 14). `SessionDir::append_log(&self, line: &str)`: opens `self.log()` with append and create, mode 0600 and `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC` on unix (`libc` added to `zygo-core` for unix), writes only when the opened handle is a regular file, writes `line` with each `\n` and `\r` as a space and one `\n`, and ignores every error. `zygo_launch::session_dir::log` is removed; its 7 callers call `sd.append_log(..)`; `statusline::data::log_width` keeps its width file and calls `dir.append_log(..)`. Effect on the launcher and the status line: a `session.log` that is a link or a FIFO is not written (before, the link was followed and a FIFO blocked the writer, which a status line must not, H§4); this refuses only a hostile file and ends no work.
