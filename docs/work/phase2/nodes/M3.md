### Final spec text (author's calls; the controller applies them)

- **W§8.4, whole section, replaced by:**

  > A launch is a member when all these are true:
  >
  > - `ZYGO_SESSION` is not set, with any value, the empty one included (not a launch inside an agent's tool).
  > - `TMUX` is set and not empty, and `$TMUX_PANE` is a tmux pane id (`%` and 1 to 10 digits). Otherwise the launch is not in tmux: a v1 launch with no tmux call and no workspace line.
  > - `ZYGO_WORKSPACE` is a valid workspace id (AU84).
  > - The pane is a workspace pane: on the server of `$TMUX` (`-S` with its socket), `display -p -t $TMUX_PANE '#{session_name} #{@zygo-ws}'` gives `zygo-<name>` and the id of `ZYGO_WORKSPACE`. Before that call, the state of that id is read: when it exists, its `tmux_socket` must be the socket of `$TMUX`; then the socket gets the AU62 check.
  > - The server URL holds no user info (AU98). A user `--settings` does not change membership (AU59).
  > - The state exists and can be read, names this tmux session, and is in phase `up` or `draining`; the pane gets its key (AU79).
  > - AU94 and W-C9 do not refuse.
  >
  > These checks are for a hand start only; `ws run` passes `LaunchOpts.member` explicitly (AU102). The checks run in the order above. A failure before the pane is known as a workspace pane is a silent v1 launch, except a state whose `tmux_socket` is not the socket of `$TMUX`, or a socket that fails AU62. The user-info check prints its AU98 line only in a workspace pane, and before any key or record is written. Every later failure prints `zygo: this agent is not saved by the workspace: <reason>` and goes on as a v1 launch: `no workspace state for <id>`; the state read error (`<path>: <reason>`, `<path>: state folder is a link`, …); `the workspace state names tmux session <a>, not <b>`; `the workspace state names tmux server <a>, not <b>` (`<a>` is `none` when unset); the AU62 text; the key error of `assign_key` (`cannot assign a key to pane <pane>: <error>`, for example `… a member starts only in phase up or draining, not down`); and, in the session callback, the reasons below. Paths and ids are escaped (C6).
  >
  > A hand start writes nothing to the member record before the launch; it only gets the pane key (W§7.4 step 4, AU79). The record is written by the launcher callback (AU34), under `lock` with the 5 s bound of launchers, in one write with the start fields: state `running`, the agent kind, `launch`, `pending` (with this zygo session and, for a fresh Claude Code start, the pre-assigned id), `config_dir` and `program` (W§8.2 step 4). In the same lock the callback checks the phase, AU94 and W-C9 again, because the state can change during the launch. When a check refuses, or the write fails, or the state is gone, the callback writes nothing, prints `zygo: this agent is not saved by the workspace: <reason>` (`a member starts only in phase up or draining, not <phase>`; `pane <key> holds resumable session <id>`; `pane <key> holds session <id>, whose launcher is still running`; `agent session <id> belongs to pane <other key>`; `no workspace state for <id>`; `could not write the member record: <error>`), and the launch goes on as a v1 launch: the callback returns `NotMember`, so the launcher drops the member before it writes the view, the settings and the agent environment (AU34). A launch that ends before the callback leaves the record of the key as it was.
  >
  > A member launcher sets `ZYGO_WORKSPACE` and `ZYGO_PANE` in the child environment (§8.4 "Set"), registers the member hooks (W§9.1), writes the membership marker into the session view (AU58), and runs the member wrapper (W§8.2). For every launch that is not a member, the launcher removes `ZYGO_WORKSPACE` and `ZYGO_PANE` from the child environment (AU58). Such a launch is a v1 launch in every other way (OP9, W-C6).

### Decisions (author's calls; they replace D1-D8 and S1, S2, S6 of the first plan)

- D1. `MemberCtx` gets `pub hand: Option<HandJoin>`, with `pub struct HandJoin { pub own_session: Option<String> }`. `ws run` passes `hand: None` (`ws.rs:234`) and keeps its rule: no record, no create. With `Some`, the callback may create or replace the record by `join`.
- D2. `join` is the one write of the start (decision 3): phase, then `conflict`, then create (or keep, for the accepted resume), then `state = Running` and `record_start`. `zygo_session` of decision 3 is `pending.zygo_session`: the committed `zygo_session` is set only by a commit (AU92).
- D3. `conflict` order: another key first (W-C9), then a live launcher on the key, then a `running`/`resumable` record with an id. `live_session` returns the zygo session id by the rule of `live_launcher` (S9).
- D4. A refusal or a failed write in the hand callback returns `NotMember`; the launcher drops the member (decision 3, S8). The callback of `ws run` never returns it.
- D5. Two refusal lines: a live launcher gets no resume command (W-C9 forbids it).
- D6. `up::socket_is_private` becomes `pub` (both `cfg` forms); the hand start runs it as `down::check_socket` does, without the missing-folder case: the `$TMUX` socket belongs to a running server.
- D7. `assign_key` uses `update_existing`; `Ok(None)` gives `Err("no workspace state")`. A test hook `snapshot::testing::before_assign(dir, hook)` fires after the read and before the lock.
- D8. `hand_start` takes `tmux: &dyn Fn() -> PathBuf`, called only after the `ZYGO_SESSION`, `TMUX`, `TMUX_PANE` and `ZYGO_WORKSPACE` checks (decision 13).
