## Capability judgment

- Security: the guard refuses agent commands (git commit, gh pr, gh release). A pattern that is too wide refuses ordinary work ("Claude Code plugin", a grep for the address); one that is too narrow lets attribution through. The patterns are fixed by §13.4 and tested both ways.
- Shared code: `guards.rs` is the one `PreToolUse` guard for both agents (Claude Code hook, OpenCode plugin); `session_text::mechanics` feeds the lead's session text and every subagent prompt on both agents; `ClaudeCode::settings` writes the file of every Claude Code session. A fault here reaches every session.

Decisions (author's call, inside the operator's rule):
- D1. Attribution is a fixed `enforce` guard like `redaction`: no `[guards]` key, not in `Guard::CONFIGURED`, it runs when work units are off and when no config loads. The operator's rule has no level to choose.
- D2. `Claude-Session:` is matched too. It is the trailer `attribution.sessionUrl` adds (schema `:1884`), and the brief says it must be off.
- D3. `claude` after `Co-Authored-By:` must be a whole word (next char not `[A-Za-z0-9_]`), so `Co-Authored-By: Claudette <c@example.com>` passes. `Generated with Claude Code` without brackets is not matched (ordinary prose can say it); the §8.6 sentence forbids it.
- D4. Only the commands of §13.4 are checked. `git tag`, `gh pr comment`, `gh api` are known limits in §13.4 and are pinned by `attribution_known_limits`, so a later widening is a visible change.
- D5. No §8.4 preflight refusal for a managed `attribution` setting (managed outranks `--settings`): the guard refuses its result. No new rule beyond the operator's.
- D6. `includeCoAuthoredBy` is deprecated in the pinned schema but still read; zygo writes both keys, as the test evidence used both.
